# 실시간 동기화 — 구현 방식 비교

"같은 공간에 있는 사람들의 위치·상태를 서로에게 보여 주는" 기능을 만드는 방법들을 정리한 문서입니다.
지금 쓰는 방식이 맞는지 판단하고, 나중에 바꿔야 할 때 근거로 쓰기 위해 남깁니다.

작성 2026-10-13 기준.

---

## 요약

**지금 방식(Supabase Realtime Broadcast)을 유지하는 것을 권합니다.**

| | 이유 |
|---|---|
| 이미 Supabase 를 쓰고 있다 | 계정·DB·실시간이 한 곳이라 인증을 다시 붙일 필요가 없다 |
| 서버를 따로 안 띄워도 된다 | 과제 기간에 서버 운영·배포가 하나 더 늘지 않는다 |
| 무료 한도가 우리 규모에 충분하다 | 아래 "메시지 예산" 참고 |
| 바꾸면 인증을 다시 설계해야 한다 | 다른 서비스는 Supabase 계정과 연결하는 작업이 따로 필요하다 |

**다만 한 가지는 고쳐야 합니다.** 지금 구조는 "서버가 판정하지 않는" 방식이라,
누군가 브라우저에서 보내는 값을 조작하면 엉뚱한 위치에 서 있게 만들 수 있습니다.
좌석 배정처럼 중요한 것은 이미 DB 가 판정하므로 괜찮지만, **위치만큼은 믿을 수 없는 값**이라는 걸
알고 있어야 합니다. 바꾸려면 "권위 있는 서버"(아래 2번 분류)가 필요합니다.

---

## 분류부터

실시간 동기화 방식은 크게 셋으로 나뉩니다. **무엇을 고르느냐보다 어느 분류인지가 먼저입니다.**

| 분류 | 누가 판정하나 | 성격 |
|---|---|---|
| **① 메시지 중계** | 아무도 안 함. 받은 걸 그대로 전달 | 쉽다. 조작에 약하다 |
| **② 권위 있는 서버** | 서버가 판정하고 결과만 내려 줌 | 정확하다. 서버를 만들고 운영해야 한다 |
| **③ 공동 편집(CRDT)** | 충돌을 자동으로 합침 | 문서·그림에 맞다. 게임 위치에는 과하다 |

지금 우리는 **①**입니다. 각자 "나 여기 있어" 를 보내고 서로 믿습니다.

---

## 방식별 정리

### 1. Supabase Realtime — Broadcast (지금 쓰는 것)

분류 ① · 이미 설치돼 있음 · 추가 비용 없음

```ts
channel.send({ type: 'broadcast', event: 'move', payload: { x, z } })
channel.on('broadcast', { event: 'move' }, ({ payload }) => { ... })
```

| 좋은 점 | 아쉬운 점 |
|---|---|
| 이미 쓰고 있어 새로 붙일 게 없다 | 서버가 판정하지 않아 값을 조작할 수 있다 |
| 로그인 계정과 그대로 연결된다 | 방마다 로직을 넣을 수 없다 (그냥 중계만) |
| 서버를 안 띄워도 된다 | 메시지 한도가 있다 (아래 참고) |
| 무료 한도가 넉넉하다 | 누가 들어왔는지는 Presence 로 따로 봐야 한다 |

> **주의**: 위치를 Presence 로 보내면 안 됩니다. `track()` 은 자주 부르라고 만든 것이 아니라서
> 0.25초마다 부르면 목록에서 사라집니다. 실제로 겪었고 `useParticipants.ts` 머리말에 기록해 뒀습니다.

### 2. Supabase Realtime — Presence

분류 ① 의 일부 · "누가 있는지" 전용

`track()` 한 번으로 "나 여기 있어" 를 등록하고, 나가면 자동으로 빠집니다.
**들어오고 나가는 것만** 담당하고, 자주 바뀌는 값에는 쓰면 안 됩니다.

지금 우리도 이 용도로만 쓰고 있습니다.

### 3. PartyKit

분류 ②(원하면) · Cloudflare Workers 위에서 방마다 서버 코드가 돈다

| 좋은 점 | 아쉬운 점 |
|---|---|
| 방마다 서버 로직을 넣을 수 있다 (판정 가능) | 서버 코드를 따로 쓰고 배포해야 한다 |
| 전 세계 가장자리에서 돌아 지연이 짧다 | Supabase 계정과 연결하는 작업이 필요하다 |
| 웹 표준(WebSocket) 기반이라 묶이지 않는다 | 배포처가 하나 더 늘어난다 (Vercel + Cloudflare) |

**우리에게**: 지금 단계에선 과합니다. "서버가 위치를 판정해야 한다" 가 필요해지면 1순위 후보입니다.

### 4. Colyseus

분류 ② · Node.js 로 직접 띄우는 게임 서버 프레임워크

| 좋은 점 | 아쉬운 점 |
|---|---|
| 방·매칭·상태 동기화가 다 들어 있다 | **서버를 띄우고 관리해야 한다** |
| 서버가 판정하므로 조작에 강하다 | 자체 운영은 무료지만 클라우드는 월 $15부터 |
| 오픈소스(MIT) | 배우고 붙이는 데 시간이 든다 |

**우리에게**: 제대로 된 게임을 만든다면 정석입니다. 다만 **8주 과제에 서버 운영을 하나 더 얹는 비용**이 큽니다.

### 5. Liveblocks

분류 ①·③ 혼합 · 협업 도구용 관리형 서비스

| 좋은 점 | 아쉬운 점 |
|---|---|
| 접속자 표시·커서·댓글이 완성품으로 제공 | **문서 협업에 맞춰져 있다.** 게임 위치는 주 용도가 아니다 |
| 붙이기 쉽다 | 무료 한도가 작고, 쓰다 보면 유료로 간다 |
| | 인증을 따로 연결해야 한다 |

**우리에게**: 맞지 않습니다. 커서·댓글이 필요한 도구가 아닙니다.

### 6. Playroom Kit

분류 ① · 캐주얼 게임용 "백엔드 없는" 서비스

| 좋은 점 | 아쉬운 점 |
|---|---|
| Three.js 를 공식 지원, 가장 빨리 붙는다 | **무료가 하루 10명까지.** 그 위는 월 $10 |
| 방 만들기·접속자 관리가 다 돼 있다 | 자체 로그인 방식이라 Supabase 계정과 겹친다 |

**우리에게**: 발표·실험에 10명이면 빠듯합니다. 계정 체계가 겹치는 것도 걸립니다.

### 7. 직접 만들기 — WebSocket (`ws`, Socket.IO)

분류 ①·② 둘 다 가능 · 서버를 직접 작성

| 좋은 점 | 아쉬운 점 |
|---|---|
| 원하는 대로 다 할 수 있다 | **서버를 쓰고, 띄우고, 관리해야 한다** |
| 배우는 게 많다 | 재접속·끊김 처리를 직접 만들어야 한다 |
| | Vercel 에는 못 올린다 (상시 연결이 필요) |

**우리에게**: 학습 목적이면 좋지만 과제 일정에는 부담입니다.

### 8. WebRTC DataChannel (P2P)

분류 ① · 브라우저끼리 직접 연결

| 좋은 점 | 아쉬운 점 |
|---|---|
| 지연이 가장 짧다 | 연결을 맺어 주는 서버가 **따로** 필요하다 |
| 서버 트래픽이 거의 없다 | 사람이 늘수록 연결 수가 제곱으로 는다 |
| | 방화벽·NAT 때문에 안 될 때가 있다 |

**우리에게**: 20명이 한 공간에 있으면 연결이 190개가 됩니다. 맞지 않습니다.

### 9. Yjs / Automerge (CRDT)

분류 ③ · 충돌을 자동으로 합치는 자료구조

**우리에게**: 맞지 않습니다. 위치는 "마지막 값이 이김" 이면 충분한데, CRDT 는 그보다 훨씬 무겁습니다.
공동 문서 편집을 넣게 되면 그때 봅니다.

## 메시지 예산 — 지금 방식이 버티는가

Supabase 무료 한도는 **월 200만 건**, 동시 접속 **200명**입니다.

지금 설정(`SEND_INTERVAL_MS = 250`)으로 계산하면:

| 상황 | 계산 | 결과 |
|---|---|---|
| 한 명이 1분 동안 계속 움직임 | 4건/초 × 60초 | **240건** |
| 3명이 1시간 테스트 | 240 × 60 × 3 | **43,200건** |
| 3명이 2시간씩 20번 테스트 | 43,200 × 2 × 20 | **1,728,000건** |

**한 달에 2시간짜리 테스트를 20번 하면 한도에 닿습니다.** 지금 쓰기엔 충분하지만 여유가 많지는 않습니다.

> 받는 쪽도 세는지(한 명이 보내면 N명이 받아서 N건인지)는 Supabase 문서에서 명확하지 않습니다.
> 그렇게 센다면 사람 수만큼 빨리 닳으므로, **실험 전에 대시보드에서 실제 사용량을 확인**하는 게 안전합니다.

### 아낄 수 있는 방법

- **움직일 때만 보낸다** — 이미 그렇게 하고 있습니다(값이 같으면 건너뜀)
- **전송 주기를 늘린다** — 250ms → 500ms 면 절반. 성능 목표가 "500ms 이하" 라 아직 여유가 있습니다
- **안 보이는 사람은 안 보낸다** — 멀리 있는 사람의 위치는 필요 없습니다. 사람이 많아지면 효과가 큽니다

## 판단

| 질문 | 답 |
|---|---|
| 지금 방식이 임의로 고른 것인가 | 아닙니다. 이미 쓰는 Supabase 안에서 자주 바뀌는 값을 보내는 **정석 방법**이 Broadcast 입니다 |
| 더 나은 게 있는가 | "서버가 판정해야 한다" 면 PartyKit·Colyseus 가 낫습니다. 그게 아니면 지금이 맞습니다 |
| 언제 바꿔야 하나 | ① 위치 조작이 문제가 될 때 ② 동시 접속이 수십 명을 넘을 때 ③ 메시지 한도에 닿을 때 |

**이번 과제 범위에서는 셋 다 해당하지 않을 가능성이 큽니다.**
