뒤쪽은 왜 이렇게 했는지, 문제가 생기면 어디를 봐야 하는지입니다.

배포할 때마다 나오는 `twoteam-xxxxx-6aimho.vercel.app` 은 그 회차 전용 주소입니다.

## 배포하기

```bash
git switch develop
git pull
npm install
./scripts/deploy.sh
```

끝입니다. 스크립트가 알아서 막아 주므로 순서만 지키면 됩니다.

**환경 변수(Supabase 주소·키)를 바꿨을 때만** `--env` 를 붙입니다.

```bash
./scripts/deploy.sh --env
```

**올리지 않고 확인만** 하려면:

```bash
./scripts/deploy.sh --dry-run
```

## 배포하기 전에 꼭 지킬 것

1. **반드시 `git pull` 부터.** CLI 배포는 "지금 내 폴더"를 그대로 올립니다. 받아오지 않으면 팀원 코드가 빠진 옛날 화면이 올라갑니다.
2. **DB를 바꿨으면 마이그레이션을 Supabase 에 먼저 적용.** 코드만 올리면 "함수를 찾을 수 없음" 같은 오류가 납니다.
3. **커밋하지 않은 파일이 없게.** `.gitignore` 에 없는 파일은 전부 같이 올라갑니다.

세 가지 모두 스크립트가 검사해서 막아 주지만, 2번(마이그레이션)은 **사람만 알 수 있어서 스크립트가 못 막습니다.**

## 배포가 멈췄을 때

스크립트가 멈추면 메시지에 무엇을 하라고 적혀 있습니다. 자주 나오는 것:

| 메시지 | 하면 되는 일 |
|---|---|
| `'xxx' 브랜치입니다. 'develop' 에서 배포하세요` | `git switch develop` |
| `커밋하지 않은 변경이 있습니다` | 커밋하거나 `git restore` |
| `원격 develop 보다 N개 뒤처져 있습니다` | `git pull && npm install` |
| `원격에 없는 커밋이 N개 있습니다` | push 하고 PR 로 합치기 |
| `lint 실패` / `build 실패` | 코드를 고치기 |
| `vercel 명령이 없습니다` | `npm i -g vercel` |

## 배포는 됐는데 화면이 이상할 때

| 증상 | 원인 | 조치 |
|---|---|---|
| **화면이 하얗게 비어 있음** | 환경 변수가 안 박힘 | `./scripts/deploy.sh --env` |
| 로그인은 되는데 **좌석·지점이 안 보임** | 마이그레이션 미적용 | Supabase SQL Editor 에서 번호 순서대로 적용 |
| **새로고침하면 404** | `vercel.json` 이 빠짐 | 저장소에 `vercel.json` 이 있는지 확인 |
| **옛날 화면이 그대로** | 받아오지 않고 배포함 | `git pull && npm install && ./scripts/deploy.sh` |

## 알아둘 제약

- **배포는 육심호만 할 수 있습니다.** Vercel 무료 플랜은 1인용이라 팀원 초대가 안 됩니다.
- **자동 배포가 아닙니다.** 팀원이 머지해도 누군가 `./scripts/deploy.sh` 를 쳐야 반영됩니다.
- **DB는 하나뿐입니다.** 배포본과 각자 로컬이 **같은 Supabase** 를 봅니다. 로컬에서 만든 계정으로 배포본에 로그인할 수 있고, 그 반대도 됩니다.

| 층 | 무엇 | 비고 |

## 2. 왜 CLI 로 배포하나

원래는 Vercel 을 GitHub 에 연결해 두면 push 할 때마다 자동으로 배포됩니다. **그게 안 됩니다.**

`CSID-DGU` 는 저장소가 971개인 학교 전체 조직입니다. 외부 앱(Vercel)이 조직 저장소를 읽으려면
**조직 소유자(조교·교수) 승인**이 필요한데, 우리는 조직 **member** 라 직접 허용할 수 없습니다.
저장소에서는 admin 이지만 조직 차원의 앱 설치 권한은 별개입니다.

**두 방식의 차이**

| | 웹 연동 | CLI |
|---|---|---|
| 코드를 가져오는 주체 | Vercel 이 GitHub 에서 | **내가 올림** |
| GitHub 권한 | 필요 (조직 승인) | **불필요** |
| 자동 배포 | 됨 | 안 됨 |
| 최신 코드 보장 | GitHub 이 진실 | **내가 pull 했는지에 달림** |

CLI 는 이미 `git clone` 으로 받아 둔 **내 폴더의 파일을 그대로 업로드**합니다.
GitHub 에 접속하지도, 권한을 요청하지도 않습니다. 그래서 승인 없이 됩니다.

보안이 약해지는 것은 아닙니다. 오히려 Vercel 이 조직 저장소에 상시 접근하지 않으니 권한 범위는 더 좁습니다.
자동화를 포기하는 대신 승인을 건너뛰는 것입니다.

**나중에 바꾸려면**: 조직 승인이 나거나 fork 를 쓰면 Vercel 대시보드 → Settings → Git 에서 연결하면 됩니다.
**프로젝트와 주소, 환경 변수는 그대로 유지**됩니다. 10분이면 됩니다.

## 3. 배포 스크립트가 하는 일

`scripts/deploy.sh` 는 올리기 전에 네 가지를 봅니다. 전부 **실제로 당할 만한 실수**를 막는 것입니다.

| 검사 | 막는 사고 |
|---|---|
| `develop` 브랜치인가 | 작업 브랜치의 미완성 코드를 배포 |
| 작업 트리가 깨끗한가 | **`.gitignore` 에 없는 파일은 전부 올라갑니다.** 실험용 파일이 섞여 배포 |
| 원격 `develop` 과 같은가 | **CLI 배포 최대의 함정.** 팀원 코드가 빠진 옛날 화면 배포 |
| lint·build 통과하는가 | 깨진 코드 배포 |

실제로 스크립트를 처음 돌렸을 때 **커밋하지 않은 임시 파일 두 개를 잡아냈습니다.** 그냥 배포했으면 같이 올라갔을 것입니다.

**기준 브랜치는 바깥에서 바꿀 수 있습니다.** 나중에 `main` 배포로 옮길 때 씁니다.

```bash
DEPLOY_BRANCH=main ./scripts/deploy.sh
```

## 4. 환경 변수

Vercel 에 두 개만 등록되어 있습니다.

| 이름 | 무엇 |
|---|---|
| `VITE_SUPABASE_URL` | Supabase 프로젝트 주소 |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | 브라우저에서 쓰는 공개 키 |

**Secret key(`service_role`)는 넣지 않습니다.** 브라우저에 그대로 노출되기 때문입니다.
Publishable key 는 노출되어도 되는 값이고, 실제 보호는 **DB 의 RLS 정책**이 합니다.

### 꼭 알아야 할 것: Vite 는 빌드할 때 값을 박아 넣습니다

`import.meta.env.VITE_*` 는 실행 중에 읽는 값이 아니라 **빌드 시점에 문자열로 치환**됩니다.
그래서 **환경 변수만 바꾸고 배포하지 않으면 예전 값이 그대로 돕니다.**

값을 바꿨다면 반드시 `--env` 를 붙여 **올리고 다시 빌드**해야 합니다.

```bash
./scripts/deploy.sh --env
```

스크립트는 `.env.local` 에서 `VITE_` 로 시작하는 줄만 읽어 갑니다.
**값은 화면에 찍지 않고 이름과 길이만** 보여 줍니다.

```
✅ VITE_SUPABASE_URL (40자)
✅ VITE_SUPABASE_PUBLISHABLE_KEY (46자)
```

`.env.local` 에는 Vercel 이 자동으로 넣은 `VERCEL_OIDC_TOKEN` 도 있는데,
`VITE_` 로 시작하지 않아 배포에 올라가지 않습니다.

## 5. DB 관리 — 제일 중요한 규칙

### 스키마 변경은 반드시 마이그레이션 파일로만

`supabase/migrations/` 에 **번호 순서대로** 파일을 추가하고, Supabase SQL Editor 에서 그 순서대로 실행합니다.

**SQL Editor 에서 테이블을 직접 고치면 안 됩니다.** 파일에 안 남으면 나중에 운영 DB 를 만들 때 그 변경이 빠지고,
"develop 에선 되는데 main 에선 안 되는" 버그가 됩니다.

지금까지의 마이그레이션은 `CLAUDE.local.md` 의 표에 정리되어 있습니다.

### 적용 순서를 지킬 것

뒤 번호가 앞 번호의 결과를 전제합니다. 예를 들어 `0003` 은 `0002` 가 만든 `slug` 값을 씁니다.
건너뛰면 조용히 0행만 들어가고 나중에 원인을 찾기 어렵습니다.

**이미 적용한 파일은 절대 다시 실행하지 않습니다.** `create table` 이 "already exists" 로 실패합니다.

### 모든 마이그레이션은 `begin; ... commit;` 으로 감쌉니다

중간에 실패하면 통째로 되돌아가, 절반만 적용된 상태가 남지 않습니다.

### 적용 전 로컬에서 검증합니다

운영 DB 에 바로 넣지 않고, 같은 버전의 PostgreSQL 컨테이너에 먼저 적용해 봅니다.

```bash
docker run -d --name pgtest -e POSTGRES_PASSWORD=test -e POSTGRES_DB=twoteam -p 55432:5432 postgres:16
```

Supabase 환경을 흉내 내려면 `auth` 스키마와 `auth.users`, `auth.uid()`,
`anon`·`authenticated` 역할을 만들고 기본 권한을 걸어야 합니다.
RLS 는 `set role authenticated; set request.jwt.claim.sub = '<uuid>';` 로 사용자를 바꿔서 확인합니다.

**테이블 소유자는 RLS 를 지나가므로, 역할을 바꾸지 않으면 정책이 없어도 다 통과합니다.**
Supabase SQL Editor 도 소유자 권한이라 **거기서는 RLS 확인이 안 됩니다.**

### `drop`·`revoke` 경고는 내용을 보고 판단

Supabase 는 그런 단어가 보이면 무조건 경고를 띄웁니다. 무엇이 지워지는지만 확인하면 됩니다.
예를 들어 뷰를 지우는 것은 **질의문 정의를 지우는 것**이지 데이터가 사라지는 것이 아닙니다.

## 6. 환경 분리 계획

| | 브랜치 | Supabase | 배포 |
|---|---|---|---|
| **지금 (개발)** | `develop` | 지금 쓰는 프로젝트 | `twoteam.vercel.app` |
| **나중 (운영)** | `main` | **아직 없음** — main 에 처음 올릴 때 새로 만든다 | 그때 Production Branch 를 `main` 으로 |

`develop` 에서 충분히 테스트한 뒤에야 `main` 으로 올립니다. 그 전까지 운영 환경은 만들지 않습니다.

**운영 DB 를 만들 때**: 빈 Supabase 프로젝트에 `0001` 부터 순서대로 돌리면 됩니다.
테이블 구조는 그대로 복제되지만 **데이터는 넘어가지 않습니다.** 계정도 좌석 기록도 새로 쌓입니다.

Vercel 은 환경별로 다른 환경 변수를 줄 수 있으므로, DB 를 나눌 때 **코드는 바뀌지 않습니다.**

**지금 DB 를 나누지 않은 이유**: 지켜야 할 운영 데이터가 아직 없고,
마이그레이션을 손으로 적용하는 상황에서 DB 가 둘이면 매번 두 번 해야 하며,
한쪽을 빠뜨리면 원인 찾기 어려운 버그가 생깁니다. 셋이 같은 데이터를 봐야 디버깅도 됩니다.

## 7. 팀원과 함께 테스트하기

배포본에서 **공유되는 것**과 **안 되는 것**이 갈립니다.

| 되는 것 | |
|---|---|
| 각자 회원가입·로그인 | 같은 Supabase 를 보므로 계정이 공유됩니다 |
| 좌석 점유 현황 | 한 명이 7번을 잡으면 다른 사람 배치도에서 회색으로 보입니다 |
| 동시에 같은 자리 누르기 | 한 명만 성공. 제안서 목표 "중복 배정 0건" 을 사람으로 검증할 수 있습니다 |
| 서로의 캐릭터 | 실시간으로 움직임·닉네임·상태 표시등이 보입니다 |

| 아직 안 되는 것 | |
|---|---|
| 로비에서 서로 보기 | 지점 안에서만 실시간이 붙어 있습니다 |
| 캐릭터 고르기 | DB 칸은 있으나 화면이 없어 모두 기본 캐릭터입니다 |
| 실제 집중 판정 | 지금은 "앉았는지" 로만 초록/노랑을 나눕니다 |

### 테스트 전 Supabase 설정 확인

**Authentication → Sign In / Providers → Email**

- **Confirm email 끄기** — 켜져 있으면 가입할 때마다 메일 링크를 눌러야 합니다
- 비밀번호 조건(최소 길이·문자 조합)은 같은 화면에서 올릴 수 있습니다

Chrome 이 "비밀번호 변경" 경고를 띄우는 경우가 있는데, **우리 서비스 문제가 아닙니다.**
입력한 비밀번호가 과거 다른 사이트에서 유출된 목록에 있다는 브라우저 경고입니다.

## 8. 비용

전부 무료 플랜입니다. 과제 규모에서는 한도에 닿지 않습니다.

| | 플랜 | 한도 | 넘으면 |
|---|---|---|---|
| Vercel | Hobby | 대역폭 100GB/월 | **다음 달까지 사이트 정지** |
| Supabase | Free | 프로젝트 2개, DB 500MB | 제한 |

Vercel Hobby 는 **상업적 사용 금지**입니다. 과제라 해당 없습니다.
빌드 결과물은 4.5MB 라 대역폭 걱정은 사실상 없습니다.

Cloudflare Pages 로 옮기면 대역폭이 무제한이지만, 지금 필요하지 않습니다.
옮기더라도 `vercel.json` 을 `public/_redirects` 로 바꾸는 정도라 20분이면 됩니다.

## 9. 배포 기록과 되돌리기

Vercel 은 배포할 때마다 그 회차의 결과물을 남깁니다.

```bash
vercel ls              # 배포 목록
vercel inspect <주소>   # 특정 배포 정보
```

문제가 생기면 대시보드에서 이전 배포를 **Promote to Production** 으로 되돌릴 수 있습니다.
**다만 DB 는 되돌아가지 않습니다.** 마이그레이션을 적용한 뒤라면 그 변경은 그대로 남습니다.
그래서 **DB 를 바꾸는 배포는 특히 조심해서** 로컬 검증을 거쳐야 합니다.
