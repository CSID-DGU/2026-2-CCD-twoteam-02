# 관리자 운영 대시보드 설계 (#590)

- 작성일: 2026-11-17
- 관련: #590 (이 문서), #591 실시간 맵(이 창에 탭으로 붙음), #592 에러 급증 Slack 알림(이 문서의 진단표·프롬프트를 씀)

## 목적

운영(main, opposeat)을 열었을 때 사용자 화면에서 생기는 문제를 팀이 직접 보고 원인을 찾는다.
지금은 서버 쪽(`usage-monitor`)만 보이고, 화면 쪽 요청 실패·끊김은 신고가 없으면 모른다.
쌓인 기록은 주간발표·최종 보고서의 근거 숫자로도 쓴다.

## 결정한 것

| 항목 | 결정 | 이유 |
|---|---|---|
| 저장 위치 | 각 환경의 Supabase(서비스·운영)에 테이블 추가 | 새 서버·키가 필요 없고 RLS·팀 확인(`is_team()`)을 그대로 쓴다. 운영은 Pro 로 올려 용량 걱정이 적다 |
| 단위 | 1분 요약 (FPS 1줄, 에러는 종류별 묶음) | 이상치 구간을 분 단위로 짚을 수 있고, 매 프레임 전송보다 수천 배 적다 |
| 보관 | 원본 90일, pg_cron 이 매일 지움 | 학기 끝까지 보고서용 원본이 남는다 |
| 들어가는 곳 | 설정 창의 팀 전용 "관리자" 탭 → 넓은 창(1100px) | `App.tsx`(팀원 담당)를 건드리지 않는다. 설정 창(640px)은 그래프에 좁다 |
| 그래프 | 라이브러리 없이 SVG | 새 의존성을 들이지 않는다 |
| 로그인 전 에러 | 모으지 않음 | 보낸 사람을 확인할 수 없고, 대부분 정상적인 실패(비밀번호 틀림)다. 게스트는 로그인으로 친다 |
| 실험 배포 | 그대로 동작해도 되지만 대상 아님 | experiment 브랜치에는 가져가지 않는다 |

## 모으는 것

### FPS (`ops_fps`, 한 사람의 1분 = 1줄)

| 칸 | 내용 |
|---|---|
| `minute` | 분 단위로 자른 시각 |
| `place` | `lobby`, `campus`, `beach`, `branch:<slug>`, `meeting` (40자) |
| `fps_avg`, `fps_min` | 그 분의 평균·최저(0.5초 구간 기준) |
| `low_seconds` | 30FPS 미만이었던 초 |
| `seconds` | 실제로 잰 초 (다른 탭에 있던 시간 제외) |
| `browser`, `os`, `mobile`, `cores`, `gpu` | 기기. `gpu` 는 WebGL 렌더러 이름 앞 80자 |
| `version` | 배포 커밋 앞 7자 (`VERCEL_GIT_COMMIT_SHA`, 로컬은 `dev`) |

- 기록용 측정기 `OpsFpsProbe` 를 따로 둔다. 기존 `FpsProbe` 는 FPS 표시를 켰을 때만 돌고 0.5초마다 화면을 다시 그린다. 새 측정기는 프레임 수만 메모리에 세고 다시 그리지 않는다.
- 붙이는 곳: `WorldScene`(광장·캠퍼스·해변), `BranchScene`, `MeetingScene` 에 한 줄씩. 장소 이름을 prop 으로 넘긴다.
- 거르는 것: 프레임 간격 1초 초과(다른 탭·창 최소화), 장면을 처음 연 뒤 5초.

### 에러 (`ops_errors`, 한 사람의 1분 동안 같은 에러 = 1줄)

| 칸 | 내용 |
|---|---|
| `minute`, `place`, `version` | 위와 같음. `place` 는 지금 주소 기준(`/space` 등) |
| `kind` | `supabase`, `relay`, `realtime`, `js` |
| `code` | HTTP 상태(`409`), 중계 닫힘 코드(`4503`), 실시간 상태(`TIMED_OUT`), JS 는 `error`/`rejection` |
| `target` | 요청 대상. 쿼리 문자열 제거, 숫자·UUID 는 `:id` 로 (예: `rpc/assign_seat`, `rest/meetings`) |
| `detail` | DB 에러 번호와 메시지 앞부분(예: `PGRST202 Could not find the function…`). `Key (…)=(…)` 처럼 입력값이 들어가는 부분은 지운다. JS 는 오류 메시지 앞부분. 120자 |
| `count` | 그 분 동안 횟수 |

잡는 곳:

- Supabase: `src/lib/supabase.ts` 의 `createClient` 에 `global.fetch` 감시를 한 겹 넣는다. 응답이 400 이상이면 본문을 복제해 에러 번호·메시지만 읽는다. `rpc/ops_report` 는 세지 않는다(실패가 실패를 부르는 고리).
- 중계 서버: `src/realtime/relayLink.ts`, `onlineLink.ts`(닫힘 코드), `useChannel.ts`(채널 조회 4xx).
- 실시간 방: Supabase 채널 구독 상태가 `CHANNEL_ERROR`, `TIMED_OUT` 일 때.
- 화면 오류: `window` 의 `error`, `unhandledrejection`.

모으지 않는 것: 웹캠 영상, 트래킹 수치, 요청·응답 본문, 입력한 글, 로그인 전 에러.

### 보내기

- `src/ops/telemetry.ts` 가 메모리에 모았다가 1분마다 `ops_report` 를 한 번 부른다. 보낼 것이 없으면 부르지 않는다.
- 보내는 곳은 이 파일 한 곳이다. 나중에 저장소를 바꾸면 여기만 바꾼다.
- 판정·정리 로직(주소 다듬기, 메시지 지우기, 분 묶기, 이상치 판정, 진단표 찾기, 프롬프트 만들기)은 `src/ops/opsLogic.ts` 순수 함수로 둔다.

## DB (`0071_ops_telemetry.sql`)

- 테이블 2개 모두 RLS 를 켜고 정책을 만들지 않는다. 화면은 함수로만 넣고 읽는다.
- `ops_report(p_fps jsonb, p_errors jsonb)` — security definer
  - `auth.uid()` 가 없으면 거절. 보낸 사람은 화면 값이 아니라 `auth.uid()`.
  - 한 번에 FPS 5줄, 에러 30줄까지.
  - `minute` 은 지금 기준 10분 전 ~ 1분 뒤만 받는다.
  - FPS 는 (사용자, 분) 유일. 같은 분이 다시 오면 무시.
  - 에러는 (사용자, 분, 종류, 코드, 대상) 유일. 같으면 횟수를 더하고 최대 10000. 한 사람의 한 분에 서로 다른 에러는 30개까지.
  - 칸마다 길이·범위 제약(check).
- `ops_dashboard(p_from timestamptz, p_to timestamptz)` — security definer, `is_team()` 이 아니면 거절. jsonb 하나로 돌려준다.
  - 요약: 보낸 사람 수, 에러 수(4xx·5xx·기타), FPS 30 미만 분 비율, FPS 중앙값
  - 시간대별: 에러 수(종류별), FPS 평균. 묶음 크기는 기간에 따라(1시간 → 1분, 24시간 → 30분, 7일 → 3시간, 30일 → 1일)
  - 상위 에러 50개: 종류·코드·대상·대표 detail·횟수·사람 수·처음·마지막·주요 브라우저·버전
  - 이상치 구간 100개: 평균 30 미만이거나 30 미만이 10초 이상인 분. 시각·장소·평균/최저·30 미만 초·기기
- 실행 권한은 `authenticated` 만.
- `pg_cron`: 매일 04:00 KST(19:00 UTC) 에 90일 지난 줄 삭제.
- 적용 순서: 서비스 DB → develop 머지. 운영 DB 는 main 에 올리기 전.

부하: 100명 접속 시 1분에 100~200번 저장. 하루 최대 약 30만 줄(100명 × 24시간 기준), 현실적으로(20명 × 8시간) 약 1만 줄.

## 화면

- 설정(`SettingsView`)에 팀원일 때만 "관리자" 탭. 안에는 최근 24시간 요약 숫자 3개와 "관리자 대시보드 열기" 버튼.
- 버튼은 `InfoPanel` 의 새 창 종류 `ops` 를 넓게(1100px) 연다.
- 대시보드 (`src/ops/OpsDashboard.tsx`)
  - 위: 어느 DB 인지(서비스/운영, Supabase 주소로 판단), 기간 버튼(1시간·24시간·7일·30일), 새로고침(1분마다 자동)
  - 요약 타일 4개: 보낸 사람, 에러(4xx/5xx), FPS 30 미만 비율, FPS 중앙값
  - 그래프 2개: 시간대별 에러 수(종류별 색), 시간대별 FPS 평균과 30 기준선
  - 표: 상위 에러, FPS 이상치 구간

## 에러 해결 돕기 (자동화 1단계)

- 진단표 `src/ops/diagnosis.ts`: (종류, 코드, 대상·detail 패턴) → 뜻, 흔한 원인, 해결 순서. 처음 넣을 항목:

| 조건 | 설명 |
|---|---|
| `PGRST202` 또는 `rpc/* 404` | 함수가 DB 에 없음 → 마이그레이션 미적용. `./scripts/check-db.sh` |
| `42501` / 403 | RLS·권한에 막힘 → 정책·grant 확인 |
| `23505` / 409 | 중복(유일 제약). `assign_seat` 등은 동시 선택 충돌이라 적으면 정상 |
| `P0001` / 400 (rpc) | 함수가 일부러 낸 안내 오류(예: 자리 없음). 급증하면 화면 흐름 확인 |
| 401 | 로그인 토큰 만료·없음 → 세션 갱신 흐름 확인 |
| 429 | 요청 한도 초과 → 어떤 화면이 반복 호출하는지 |
| 5xx | Supabase 쪽 장애·타임아웃 → 상태 페이지, `usage-monitor` |
| 중계 `4503` | 정원 초과 → 채널 인원, `TOTAL_CAPACITY` |
| 중계 401 / 1006 | 토큰 확인 실패·연결 끊김 → Worker 비밀값, 네트워크 |
| 실시간 `TIMED_OUT`·`CHANNEL_ERROR` | Realtime 한도·장애·RLS → 사용량, 방 정책 |
| `js` | 메시지로 코드 검색 |

- 에러 줄을 누르면 설명과 "AI 프롬프트 복사" 버튼. 프롬프트에는 요약(종류·코드·대상·detail·횟수·사람 수·처음/마지막·장소·브라우저·버전), 진단표 설명, 찾아볼 명령(`rg "<대상 이름>" supabase/migrations src relay/src`), 답 형식(원인 → 수정안 → 확인 방법), 저장소 규칙(CLAUDE.md 를 먼저 읽을 것)이 들어간다.

## 확인 방법

1. 로컬 Postgres 컨테이너에 0001~0071 을 적용하고, 역할을 바꿔 가며 확인한다: 남의 이름으로 넣을 수 없음, 상한, 시각 범위, 팀이 아니면 `ops_dashboard` 거절, 직접 select 불가.
2. `npm run lint`, `npm run build`.
3. 서비스 DB 에 0071 적용 후 개발 서버에서: 없는 함수를 부르는 에러, 중계 연결 실패, CPU 부하로 FPS 저하를 일부러 만들고 1~2분 안에 대시보드에 나오는지 본다. 팀이 아닌 계정으로 관리자 탭이 안 보이는지도 본다.
