# 실험 설문 화면 설계 (CSV 저장)

작성 2026-10-23. Issue #201. 브랜치는 `experiment`에서 딴다(실험 전용 코드).

## 왜

사용자 실험(`docs/사용자-실험-재설계.md`)은 실험 시작 전 1회, 조건이 끝날 때마다 3회, 마무리 1회 설문을 받는다. 문항은 `docs/실험-설문지.md`에 정리돼 있다(팀 검토 전 초안). 응답은 종이나 외부 폼이 아니라 **웹 화면에서 받아 참가자 번호와 함께 CSV로 남기기**로 했다(2026-10-23). 이유는 과제 창 CSV와 같은 꼴로 바로 분석에 쓰고, 문항이 보인 뒤 답하기까지의 시간도 남기기 위해서다.

## 목표 / 비목표

- 목표: 진행자가 참가자 번호·시점을 넣고 열면, 그 시점의 문항이 묶음별로 나오고, 다 답하면 CSV가 내려받아진다. 문항 문서가 바뀌면 **데이터 파일 한 곳**(`surveyItems.ts`)만 고치면 된다. 로그인·Supabase·웹캠을 쓰지 않는다.
- 비목표: 응답을 서버에 올리기(실험 자료는 로컬 CSV로 관리, 6-5절), 과제 창과의 자동 연결(과제 창 #191이 정해지면 그쪽에서 이 화면의 주소를 열면 된다), 인터뷰 녹음, 분석.

## 화면

주소 `/survey.html` (별도 입구. `task-try.html`과 같은 방식이라 앱 라우터·로그인 울타리 밖). 코드는 `src/experiment/survey/`.

1. **시작 화면** — 참가자 번호(P01 꼴), 시점(`pre` 사전 / `A` / `B` / `C` / `final` 마무리), 조건 순서(ABC 중 하나의 순열, 예 `CBA`). 주소에 `?participant=P07&phase=B&order=CBA`가 있으면 미리 채운다. 이 브라우저에 저장된 응답이 있으면 "전체 CSV 내려받기" 버튼이 함께 보인다.
2. **문항 화면** — 묶음(`docs/실험-설문지.md`의 ①~⑥, 사전은 1-1→1-2→1-3→K-SSAS 기준선(① 재사용)) 하나가 한 페이지. 위에 묶음 안내문, 아래에 문항과 선택지(라디오). 모든 문항에 답해야 "다음"이 켜진다. 뒤로 가기 없음(상태 척도라 되돌아가 고치는 것을 막는다 — 우리 판단). 조건 끝 설문은 ①→⑥ 순서 고정.
3. **끝 화면** — "저장되었습니다." + CSV 자동 내려받기 + 다시 내려받기 버튼. 참가자가 보는 화면이라 점수·결과는 보여 주지 않는다.
4. `final`(마무리)은 **진행자가** 채운다: 선호 순위(세 조건을 끌어서 정렬하는 대신 1·2·3위 선택 상자), 의심 확인 SUSP_1(예/아니오/잘 모르겠다)·SUSP_2(메모), 자료 사용 철회 WITHDRAW(예/아니오). 인터뷰 INT_1~5의 답은 녹음·메모로 남기므로 화면에 넣지 않는다.

### 조건에 따라 달라지는 글자

- 공존감(NM_1~8)의 "(the room)" 자리: 기본 상수 `PLACE_WORD = { A: "공간", B: "열람실", C: "열람실" }`. 팀이 통일하기로 하면 상수만 바꾼다.
- B 조건에는 공존감·카메라 묶음 위에 안내문: "이번 세션에는 함께 있던 사람이 없었습니다. 그렇더라도 느낀 대로 답해 주세요."
- 참가자 화면에 조건 이름(A/B/C)이나 "혼자/함께"는 띄우지 않는다(기존 `condition.ts` 원칙). 시점 선택은 시작 화면(진행자)에서만 보인다.

## 데이터 (`surveyItems.ts`, 순수 데이터)

```ts
type Scale = { kind: "likert"; min: number; max: number; labels: Record<number, string> }  // 라벨은 양 끝과 중간만 있어도 됨
           | { kind: "choice"; options: string[] }
           | { kind: "text" }
type Item = { code: string; text: string; scale: Scale; reverse?: boolean }
type Group = { id: string; title: string; note?: string; items: Item[]; noteByPhase?: Partial<Record<Phase, string>> }
type Phase = "pre" | "A" | "B" | "C" | "final"
const GROUPS_BY_PHASE: Record<Phase, Group[]>
```

- 문항 텍스트·코드·척도는 `docs/실험-설문지.md`를 그대로 옮긴다. 문서가 바뀌면 이 파일을 같이 고친다(문서가 기준).
- `{장소}` 자리표시를 두고 화면이 `PLACE_WORD[phase]`로 바꿔 넣는다.
- 역문항은 `reverse: true`로 표시만 하고 **저장은 원 응답 그대로**(문서 3절).

## 저장

- 답할 때마다 `localStorage`(`survey:v1:<참가자>`)에 누적한다. 새로고침·실수로 닫아도 남는다. 다른 참가자가 같은 컴퓨터를 쓰면 번호가 다르니 섞이지 않는다.
- 시점이 끝나면 그 시점의 행만 CSV로 내려받는다. 파일 이름 `survey-P07-B-2026-11-10-14-32-10.csv`. 시작 화면의 "전체 CSV 내려받기"는 그 참가자의 모든 시점을 한 파일로.
- CSV 열(문서 3절 그대로): `participant, phase, order, code, value, answered_at, ms_since_shown`. BOM 포함(엑셀 한글). 쉼표·따옴표는 CSV 규칙대로 감싼다.
- `ms_since_shown`은 그 묶음 페이지가 보인 시각부터 그 문항에 (마지막으로) 답한 시각까지.
- **중간에 끊기면 이어 간다.** 응답 행과 별도로 진행 상태(`survey:v1:<참가자>:progress` — 시점, 현재 묶음 번호, 묶음이 보인 시각)를 저장한다. 같은 참가자·시점으로 다시 열면 시작 화면이 "B 설문 3번째 묶음부터 이어 합니다"라고 알리고 그 묶음부터 보여 준다. 새로고침 뒤 `ms_since_shown`은 묶음이 **다시 보인 시각**부터 센다(끊긴 시간을 응답 시간에 넣지 않음). 같은 문항에 두 번 답하면 마지막 값만 한 행으로 남긴다.
- 끝까지 마친 시점을 다시 열면 "B 설문은 이미 끝났습니다. 다시 하면 응답이 덧붙여집니다(덮어쓰지 않음)"라고 알리고 진행자가 고른다. 덧붙인 행은 `answered_at`으로 구분한다.

## 빌드 포함

Vite는 기본으로 `index.html`만 빌드한다. `task-try.html`처럼 두면 개발 서버에서만 열리고 배포본에는 안 들어간다. 실험은 배포본(`docs/배포와-운영.md`의 experiment 배포)으로 할 수 있어야 하므로 `vite.config.ts`에 다중 입구(`build.rollupOptions.input`: `index.html`, `survey.html`, `task-try.html`)를 등록한다. 확인은 `npm run build && npm run preview` → `/survey.html`.

## 추가 (2026-10-23 밤): 과제 자리에 실제 과제를 넣음

사용자 결정: 과제 종류는 아직 안 정했지만 계산·오탈자 둘 다 넣어 팀원이 **실제처럼 전체(사전 설문 → 과제 → 설문 ×3 → 마무리)**를 돌려 보고, 과제·설문 내용과 흐름에 대한 피드백을 받는다. 설문 문항·문제는 나중에 바꾼다.

- 시작 화면(진행자)에서 **과제 종류**(① 단순 계산 / ② 오탈자 찾기)와 **과제 시간**(20분 본 실험 / 5분 예비·연습 / 2분 화면 점검)을 고른다. 주소 `?task=typo`로 미리 고를 수 있다. 세션이 시작되면 바꿀 수 없다(세 조건이 같은 과제여야 하므로).
- 과제 문항 화면(`CalcTask`·`TypoTask`)과 문제 생성·지문·채점 로직을 과제 후보 시험(spike)에서 `src/experiment/task/`(`taskLogic.ts`, `TaskItems.tsx`)로 옮기고, spike는 그것을 가져다 쓴다(지문·규칙을 한 곳에서 고치게). 과제 단계 화면은 `TaskPanel.tsx`.
- 조건마다 문제 시드를 과제 시작 시각으로 정해 `SessionProgress.taskSeed`에 두고, 모든 과제 행에 `seed` 열로 남긴다. 새로고침하면 이미 답한 수(`skip`)만큼 건너뛰어 같은 문제가 다시 나오지 않는다.
- 과제 기록은 조건별로 `survey:v1:<참가자>:task:<조건>`에 답마다 저장하고, 시간이 끝나면 `task-P01-B-날짜.csv`를 내려받는다. 열: `participant, condition, order, kind, seed, index, shown_ms, answered_ms, elapsed_ms, problem, answer, input, correct, detail, missed, wrong, answered_at`. 끝 화면에서 세 조건 합본 `task-P01-all-….csv`.
- 시간이 끝나면 "시간이 끝났습니다 → 설문으로" 화면이 뜬다. 진행자용 "과제 일찍 끝내기"(확인 창)는 예비·연습용이며 본 실험에서는 쓰지 않는다.
- "최대 5분 더"(자발적 지속, 재설계 문서 열린 문제)는 넣지 않았다.

## 추가 (2026-10-23 밤 2): 오탈자 지문 60개, 조건별 세트 3개

사용자 질문("같은 문제 두 번 하는 것보다 필사를 다시 넣을까")에 대한 답: 세 조건은 **같은 과제**여야 하고(달라지는 것은 함께 있는 사람뿐), "같은 문제"는 **세트**로 푼다(재설계 문서 3절 "세트 3개 + 연습 1개").

- 지문을 26개에서 **60개**로 늘리고(모두 직접 씀, 교과서 투, 오타 1~3개), 번갈아 배정으로 **세트 3개 × 20개**로 나눈다(`TYPO_SETS`). 세트끼리 겹치지 않는다.
- k번째 조건에 쓸 세트 = k (`setFor`). 재설계 문서 3절 "문제 세트는 항상 1→2→3 순서" 그대로다. 조건 순서가 라틴 방격으로 돌아가므로 각 세트가 각 조건과 같은 횟수로 만난다. (처음에는 참가자 번호로 돌리는 안을 넣었다가 문서와 맞추어 되돌림.) 계산은 조건마다 시드가 달라 세트 개념 없이도 다른 문제가 나오지만, 기록을 맞추려 같은 세트 번호를 적는다.
- 과제 CSV에 `set` 열(1~3)을 추가한다.
- 과제 후보 시험(spike)은 세트 없이 60개 전체를 섞어 쓴다.
- 20분 본 실험에는 세트당 약 70개가 필요하므로(지문당 17초 기준), 오탈자로 정해지면 세트당 50개씩 더 쓴다. 5분 예비·연습에는 20개로 충분하다.

## 추가 (2026-10-23 밤 3): 실험 방식 — 본 실험 / 과제 비교(팀 피드백용)

사용자 결정: 팀원 시험에서는 과제 종류를 3번째 과제에서만 고르게 한다. 1·2번은 계산·오탈자를 한 번씩 하고, 3번은 마음에 든 것이든 확인하고 싶은 것이든 하나를 다시 한다. 그래서 어느 과제든 한 번은 두 번 해 보게 되고, 그 피드백으로 과제 종류를 정한다.

- 시작 화면에 **실험 방식** 선택: `experiment`(본 실험: 한 과제로 세 번, 과제 종류를 시작 때 고름) / `compare`(과제 비교: 1·2번은 참가자 번호 홀수면 계산→오탈자, 짝수면 오탈자→계산, 3번은 시작 안내 화면에서 고름). 주소 `?mode=compare`. 세션이 시작되면 바꿀 수 없다.
- `SessionProgress.mode`, `kindsByPosition`(조건 차례별 과제, 3번째는 고르기 전까지 비어 있음). `kindForPosition(progress, position)`이 그 조건의 과제를 준다. 3번째 조건의 시작 안내 화면은 과제를 고르기 전까지 "과제 시작"이 잠긴다.
- 과제 CSV의 `kind` 열에 실제로 한 과제가 남는다. 오탈자가 1번과 3번(또는 2번과 3번)에 오면 세트가 달라(`setFor`가 조건 차례로 정함) 지문이 겹치지 않는다.
- 마무리 묶음에 `FEEDBACK`(자유 메모) 문항을 더해 진행자가 참가자의 과제·설문·흐름 피드백을 적는다. 본 실험에서는 비워 둔다.
- 본 실험은 반드시 `experiment` 방식으로 한다. `compare`는 과제 종류를 정하기 위한 팀 내부용이다.
