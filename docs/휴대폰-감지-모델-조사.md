# 새 모델보다 귀 옆 규칙이 먼저다

> **덧붙임 (2026-11-16).** 2026-11-15에 공개 자료만 보고 쓴 조사 보고서다. 그 뒤 같은 영상으로 직접 재 보니 결론이 달라졌다. 받아 온 모델은 어느 것이든 귀 옆 손을 휴대폰으로 잡았고, PP-PicoDet-M이 휴대폰을 가장 잘 잡았으며, 우리 영상으로 다시 학습시키자 귀 옆 손 오판이 사라졌다. 그래서 귀 옆 규칙 대신 **PP-PicoDet-M을 우리 영상으로 학습시키는 쪽**으로 정했다. 측정값과 지금의 결론은 [휴대폰-모델-비교.md](휴대폰-모델-비교.md)에 있다. 이 보고서는 후보 모델의 공개 수치, 라이선스, 학습 도구의 상태를 찾아볼 때 쓴다.

지금 코드에 그대로 끼워 넣을 수 있으면서 EfficientDet-Lite0보다 가볍고 휴대폰을 더 잘 찾는다고 **확인된** 모델은 없다. MediaPipe ObjectDetector가 받는 기성 모델은 Lite0·Lite2·SSD MobileNetV2 세 가지뿐이고 셋 다 COCO로 학습해 휴대폰만 안다. 종이 위 수치가 더 좋은 후보(PP-PicoDet는 Apache-2.0, YOLO26n은 AGPL-3.0)는 전부 실행 라이브러리를 하나 더 넣어야 하고, 휴대폰 한 종류에 대한 정확도나 브라우저에서 잰 속도는 어디에도 공개돼 있지 않아 직접 재기 전에는 "더 낫다"고 말할 수 없다. 휴대폰과 태블릿을 함께 아는 작은 모델(YOLOv8n-OIV7 7.2MB, YOLO26n-Objects365 6.0MB)은 바로 내려받을 수 있지만 모두 AGPL-3.0이다. 가장 먼저 없애야 하는 귀 옆 맨손 오판은 모델을 바꿔서 풀린다는 근거가 없다. 읽은 문헌 가운데 귀 옆 맨손과 귀 옆 휴대폰을 갈라 낸 결과를 보고한 것이 하나도 없고, 지금 방어할 수 있는 방법은 얼굴 랜드마크로 만든 귀·볼 영역 안의 검출을 휴대폰 판정에서 빼는 규칙이다(대가로 귀에 댄 실제 통화는 놓친다). 발열에서도 1초에 한 번 도는 감지기의 계산 몫은 작다고 추정되며, 감지기 쪽에서 줄일 수 있는 것은 계산량보다 "3D 화면과 GPU를 나눠 쓰는 다툼"이다. 그래서 추천은 한 줄로 이렇다: 팀 시험 영상으로 기준선을 먼저 재고, 새 라이브러리 없이 되는 세 가지(귀·볼 억제 규칙 → int8 모델과 CPU 실행 → 손 주변 잘라 넣기)를 순서대로 해 본 뒤, 그래도 모자랄 때만 직접 학습이나 라이브러리 추가로 넘어간다.

> **읽는 법.** 조사일은 2026-11-15다. 표시가 없는 수치는 조사자가 공식 문서·저장소·API를 직접 가져와 읽은 것이다. 다만 문서 페이지 상당수는 가져오기 도구의 요약을 거쳐 읽었으므로 표를 옮기는 과정의 오독 가능성이 조금 있다. **(스니펫)** 은 검색 결과 요약만 보고 원문은 못 연 것, **(기억)** 은 조사자의 기억에 의존해 확인하지 못한 것, **(추정)** 은 출처가 아니라 조사자의 계산·해석, **(일화)** 는 사용자 한 명의 보고, **확인 못 함** 은 찾지 못했거나 열지 못한 것이다. 속도 수치는 따로 적지 않는 한 전부 휴대폰·PC의 네이티브 실행값이고 **브라우저에서 잰 값이 아니다.**

## 그대로 끼울 수 있는 더 나은 기성 모델은 없고, 나머지는 실행 라이브러리를 하나 더 요구한다

용어부터 정리한다. **감지 모델**은 사진에서 물체가 어디 있는지 상자로 찾아 주는 모델이다. **mAP**는 여러 물체 종류에 대해 얼마나 잘 찾고 상자를 얼마나 정확히 치는지를 평균한 점수로, 높을수록 좋다. **파라미터**는 모델이 학습으로 얻은 숫자의 개수로 파일 크기를 대략 정한다. **FLOPs**는 추론 한 번에 드는 계산량이다. **양자화**는 모델 안의 숫자를 더 작은 자료형으로 바꿔 파일과 계산을 줄이는 일이고, float16은 16비트 실수, int8은 8비트 정수로 바꾼 것이다. **위임(delegate)** 은 MediaPipe가 계산을 CPU에 시킬지 GPU에 시킬지 고르는 옵션이다. **실행 라이브러리(런타임)** 는 모델 파일을 읽어 실제 계산을 돌리는 프로그램이다.

지금 구성은 EfficientDet-Lite0 float16 모델을 GPU 위임으로 돌리고, 점수 0.3 이상인 "cell phone" 하나만 받는다. 얼굴·자세 모델도 GPU 위임이다(현재 브랜치의 `src/tracking/useTracking.ts`에서 확인).

### MediaPipe가 받는 모델 형식이 선택지를 둘로 가른다

MediaPipe ObjectDetector는 아무 감지 모델이나 받지 않는다. 모델이 내놓는 숫자 묶음(출력 텐서)이 **정확히 4개**(상자·종류·점수·개수. 겹친 상자를 하나로 정리하는 후처리인 NMS가 모델 안에 들어 있는 방식)이거나 **2개**(상자와 점수. SSD라는 옛 방식의 기준 상자 정보가 모델 설명서에 들어 있는 방식)인 TFLite 파일만 받고, 그 밖에는 오류를 낸다 ([MediaPipe 후처리 그래프 소스](https://github.com/google-ai-edge/mediapipe/blob/master/mediapipe/tasks/cc/components/processors/detection_postprocessing_graph.cc)). 공식 가이드도 커스텀 모델은 TFLite 형식에 모델 설명서(메타데이터)가 들어 있어야 한다고 적는다 ([MediaPipe Object Detector 가이드](https://developers.google.com/edge/mediapipe/solutions/vision/object_detector)). YOLO 계열은 출력이 하나라 이 검사에서 바로 떨어진다. YOLO를 이 형식에 맞춰 넣은 공식 문서나 동작하는 예제는 찾지 못했다. 모델 내부를 고쳐 출력을 4개로 쪼개는 길이 이론상 있지만 검증된 적이 없고, 초보 팀이 몇 주 안에 할 일이 아니다(추정).

이 제약 때문에 후보는 "MediaPipe가 배포하는 모델로 주소만 바꾸는 것"과 "실행 라이브러리를 하나 더 넣어 따로 돌리는 것"으로 갈린다.

### 새 라이브러리 없이 되는 것: MediaPipe 배포 모델 3종

| 모델 | 입력 크기 | COCO mAP | 파일 크기 | Pixel 6 CPU / GPU 지연 | 휴대폰·태블릿 |
|---|---|---|---|---|---|
| EfficientDet-Lite0 float16 (현재) | 320 | 26.41 | 7.25MB | 53.97ms / 27.97ms | 휴대폰만 |
| EfficientDet-Lite0 int8 | 320 | 26.10 | 4.60MB | 29.31ms / 값 없음 | 휴대폰만 |
| EfficientDet-Lite2 float16 | 448 | 35.06 | 12.14MB | 198.77ms / 47.31ms | 휴대폰만 |
| EfficientDet-Lite2 int8 | 448 | 34.69 | 7.52MB | 70.91ms / 값 없음 | 휴대폰만 |
| SSD MobileNetV2 float16 | 256 | 확인 못 함 | 5.92MB | 37.35ms / 28.16ms | 휴대폰만 |

지연 시간과 모델 목록은 MediaPipe 가이드, mAP와 파라미터 수(Lite0 3.2M)는 EfficientDet 원 저장소, 파일 크기는 배포 주소의 파일 길이를 직접 조회한 값이다 ([MediaPipe Object Detector 가이드](https://developers.google.com/edge/mediapipe/solutions/vision/object_detector), [google/automl EfficientDet README](https://github.com/google/automl/blob/master/efficientdet/README.md), [Lite0 int8 배포 파일](https://storage.googleapis.com/mediapipe-models/object_detector/efficientdet_lite0/int8/latest/efficientdet_lite0.tflite)).

이 표에서 읽을 것은 세 가지다. 첫째, **int8은 가벼워질 뿐 정확해지지 않는다.** 파일이 37% 작고 Pixel 6 CPU에서 46% 빠르지만 mAP는 26.41에서 26.10으로 오히려 조금 내려간다. 둘째, **Lite2는 무겁다.** 같은 기기 CPU에서 Lite0의 약 3.7배다. 팀이 2026-10-16에 직접 잰 결과에서도 화면에 보이게 든 휴대폰은 Lite0 96%, Lite2 95%로 차이가 없었다(`src/tracking/useTracking.ts` 주석. 이번 조사에서 다시 재지 않았다). COCO mAP가 9점 높은 모델이 우리 장면에서는 낫지 않았다는 뜻이다. 셋째, **Lite0보다 가벼운 기성 모델은 SSD MobileNetV2 하나인데** mAP가 공개돼 있지 않고, 같은 세대 SSD MobileNetV2의 COCO mAP가 22 수준이라 휴대폰 감지가 나아질 가능성은 낮다(추정) ([TF1 감지 모델 목록](https://github.com/tensorflow/models/blob/master/research/object_detection/g3doc/tf1_detection_zoo.md)).

### 하나 더 넣어야 되는 것: Apache-2.0 경량 모델과 YOLO

아래 후보는 전부 MediaPipe에 들어가지 않는다. 감지기만 다른 실행 라이브러리로 따로 돌려야 하고, 영상 프레임을 모델 입력으로 바꾸는 전처리와 결과를 상자로 푸는 후처리도 직접 짜야 한다. **ONNX**와 **TFLite**는 모델 파일 형식의 이름이다.

| 모델 | 입력 | 파라미터 | 계산량 | COCO mAP | 파일 크기 | 라이선스 (코드·가중치) | 필요한 실행 라이브러리 |
|---|---|---|---|---|---|---|---|
| PP-PicoDet-S | 320 | 1.18M | 0.97G | 29.1 | 확인 못 함 (추정 약 4.7MB) | Apache-2.0 | `onnxruntime-web` |
| PP-PicoDet-S | 416 | 1.18M | 1.65G | 32.5 | 위와 같음 | Apache-2.0 | `onnxruntime-web` |
| PP-PicoDet-M | 320 | 3.46M | 2.57G | 34.4 | 확인 못 함 (추정 약 14MB) | Apache-2.0 | `onnxruntime-web` |
| NanoDet-Plus-m | 320 | 1.17M | 0.9G | 27.0 | ONNX 4.79MB | Apache-2.0 | `onnxruntime-web` |
| NanoDet-Plus-m | 416 | 1.17M | 1.52G | 30.4 | 위와 같음 | Apache-2.0 | `onnxruntime-web` |
| YOLOX-Nano | 416 | 0.91M | 1.08G | 25.8 | ONNX 3.66MB | Apache-2.0 | `onnxruntime-web` |
| RTMDet-tiny | 640 | 4.8M | 8.1G | 41.1 | 확인 못 함 | Apache-2.0 | `onnxruntime-web` |
| D-FINE-N | 640 | 4M | 7G | 42.8 | ONNX 15.26MB, int8 4.48MB | Apache-2.0 (COCO 체크포인트) | `onnxruntime-web` 또는 Transformers.js |
| YOLO26n | 640 | 2.4M | 5.5B | 40.9 | ONNX 9.94MB, int8 2.85MB | **AGPL-3.0** | LiteRT.js 또는 `onnxruntime-web` |
| YOLO11n | 640 | 2.6M | 6.5B | 39.5 | ONNX 10.93MB | **AGPL-3.0** | 위와 같음 |

수치 출처는 각 저장소의 공식 표다 ([PP-PicoDet README](https://github.com/PaddlePaddle/PaddleDetection/blob/release/2.8/configs/picodet/README_en.md), [NanoDet README](https://github.com/RangiLyu/nanodet), [YOLOX README](https://github.com/Megvii-BaseDetection/YOLOX), [RTMDet 설정](https://github.com/open-mmlab/mmdetection/tree/main/configs/rtmdet), [D-FINE README](https://github.com/Peterande/D-FINE), [YOLO26 문서](https://docs.ultralytics.com/models/yolo26/), [YOLO11 문서](https://docs.ultralytics.com/models/yolo11/), [DEIMv2 README](https://github.com/Intellindust-AI-Lab/DEIMv2)). ONNX 파일 크기는 Hugging Face 파일 목록을 직접 조회했다 ([dfine_n_coco-ONNX](https://huggingface.co/api/models/onnx-community/dfine_n_coco-ONNX/tree/main/onnx), [yolo26n-ONNX](https://huggingface.co/api/models/onnx-community/yolo26n-ONNX/tree/main/onnx)).

**Lite0와 비슷한 무게로 mAP가 더 높은 Apache-2.0 후보는 PP-PicoDet-S(320: 29.1, 416: 32.5)와 PP-PicoDet-M 320(34.4), NanoDet-Plus-m 416(30.4)이다.** PP-PicoDet-M 320은 Lite2에 가까운 점수를 Lite0의 2~3배쯤 되는 계산으로 낸다(추정. Lite0의 FLOPs는 확인하지 못했고, 320 입력에서 1B 안팎으로 기억한다). 유지 상태는 고르지 않다. PaddleDetection은 2026-05까지 갱신됐지만 NanoDet과 mmdetection(RTMDet)은 2024-08 이후 멈춰 있다 ([GitHub API](https://api.github.com/repos/open-mmlab/mmdetection)).

**"YOLO는 무겁다"는 생각은 입력 크기에 달렸다.** YOLO26n의 5.5B는 640 입력 기준이다. 계산량은 입력 넓이에 비례하므로 320으로 내보내면 약 1.4B, 416이면 약 2.3B로 추정된다. 다만 입력을 줄였을 때의 mAP는 공식 표에 없고 640 값보다 낮아진다. Ultralytics는 YOLO26n이 YOLO11n보다 CPU에서 최대 43% 빠르다고 적는다 ([YOLO26 문서](https://docs.ultralytics.com/models/yolo26/)).

후보에서 뺀 것도 적어 둔다. RF-DETR Nano는 파라미터 30.5M에 ONNX 108MB로 Lite0의 약 10배이고, RT-DETRv2-S는 20M이다 ([RF-DETR README](https://github.com/roboflow/rf-detr), [RT-DETR README](https://github.com/lyuwenyu/RT-DETR)). YOLO-NAS는 가중치를 남에게 배포하는 것 자체를 금지해 브라우저로 내려보내는 구조와 맞지 않는다 ([YOLO-NAS 가중치 라이선스](https://raw.githubusercontent.com/Deci-AI/super-gradients/master/LICENSE.YOLONAS.md)). Edge Impulse FOMO는 상자가 아니라 물체 중심점만 내고 COCO로 학습된 가중치가 없다 ([FOMO 문서](https://docs.edgeimpulse.com/docs/edge-impulse-studio/learning-blocks/object-detection/fomo-object-detection-for-constrained-devices)). YOLOX-Nano(25.8)는 Lite0보다 점수가 낮다.

**실행 라이브러리는 세 가지가 있고, 어느 것이든 "새 라이브러리 추가"라 팀 확인 대상이다.** `onnxruntime-web`(MIT)은 Apache-2.0 계열 모델이 모두 ONNX를 공식 지원하므로 후보 폭이 가장 넓다. CPU(WASM) 실행은 모든 연산을 지원하고, 아주 가벼운 모델은 CPU 실행으로 충분할 수 있다고 문서가 적는다 ([ONNX Runtime Web 개요](https://onnxruntime.ai/docs/tutorials/web/), [WebGPU 문서](https://onnxruntime.ai/docs/tutorials/web/ep-webgpu.html)). `@litertjs/core`(LiteRT.js, Apache-2.0)는 Google이 내놓은 것으로 `.tflite`를 그대로 읽기 때문에 지금 쓰는 Lite0 파일과 YOLO 내보내기를 같은 라이브러리에서 비교할 수 있고, Ultralytics가 브라우저용 공식 경로로 안내한다 ([LiteRT.js 문서](https://developers.google.com/edge/litert/web), [Ultralytics LiteRT 문서](https://docs.ultralytics.com/integrations/litert/)). `@huggingface/transformers`(Apache-2.0)는 D-FINE을 전·후처리까지 한 줄로 쓰게 해 주지만 안에서 ONNX Runtime Web을 쓰므로 묶음이 더 클 것이다(추정). 세 라이브러리의 묶음 크기는 확인하지 못했다.

**라이선스는 이렇게 갈린다.** AGPL-3.0은 "이 코드나 모델을 넣은 프로그램을 남에게 제공하면 프로그램 전체 소스를 같은 조건으로 공개해야 한다"는 라이선스다. Ultralytics는 자사 YOLO(v5·v8·11·12·26)로 학습한 모델이 기본으로 AGPL-3.0이고, 사전학습 가중치를 쓰지 않고 처음부터 직접 학습해도 적용되며, 지키려면 파생물 전체의 소스를 공개해야 한다고 적는다. 대학 수업 과제와 소스를 전부 공개하는 프로젝트는 무료 범위에 든다 ([Ultralytics License](https://www.ultralytics.com/license)). 우리 저장소는 이미 공개라 "소스 공개" 요건은 채울 수 있다. 실제 부담은 **저장소 전체에 AGPL-3.0을 명시해야 하고, 나중에 다른 라이선스로 바꾸거나 비공개·상용으로 돌리려면 모델을 다시 갈아야 한다**는 점이다. 지금 저장소에는 LICENSE 파일도 `package.json`의 라이선스 항목도 없으므로(로컬 확인) 이것은 팀 전원이 정할 일이다. 이 해석은 Ultralytics 자체 설명에 근거하며, AGPL 조문을 직접 읽은 것도 법률 자문도 아니다. `@ultralytics/yolo` npm 패키지의 라이선스는 확인하지 못했다. Apache-2.0과 MIT는 라이선스 사본과 저작권 고지만 붙이면 되고 우리 코드의 라이선스를 묶지 않는다. DEIMv2는 수치가 가장 좋지만 비상업 목적에 한해 쓰게 하는 자체 라이선스이고 앞부분만 읽었다 ([DEIMv2 LICENSE](https://raw.githubusercontent.com/Intellindust-AI-Lab/DEIMv2/main/LICENSE.md)).

### 이 표가 말해 주지 않는 것

표의 mAP는 COCO 80종의 평균이다. **"cell phone" 한 종류의 점수는 어느 모델도 공개하지 않았고**, 웹캠 책상 장면에서의 검출률은 더더욱 없다. 위에서 본 대로 팀 측정에서 mAP가 높은 Lite2가 낫지 않았으니, 이 표는 "시험해 볼 순서"를 정하는 데만 쓸 수 있다. 속도도 마찬가지다. 이 모델들을 브라우저(내장 GPU나 CPU WASM)에서 프레임당 ms로 잰 믿을 만한 공개 자료는 찾지 못했다. LiteRT.js가 ONNX Runtime Web보다 "보통 2배쯤 빠르다"는 말은 Ultralytics의 주장이고 수치와 기기가 없다 ([Ultralytics LiteRT 문서](https://docs.ultralytics.com/integrations/litert/)). 따라서 질문 (1)의 답은 "후보는 있다, 더 낫다는 증거는 없다"이다.

## 휴대폰과 태블릿을 함께 아는 작은 모델은 있지만 전부 AGPL·GPL이고, 더 낫다는 증거가 없다

### 태블릿을 아는 데이터는 Open Images와 Objects365 둘뿐이다

감지 모델은 학습 데이터에 있던 물체 종류(클래스)만 안다. COCO에는 태블릿이 없고, COCO 이미지에 1,203종을 다시 붙인 LVIS에도 이름이나 동의어에 tablet이 들어간 종류가 없다 ([LVIS v1 클래스 목록](https://raw.githubusercontent.com/facebookresearch/detectron2/main/detectron2/data/datasets/lvis_v1_categories.py)). 태블릿이 있는 범용 데이터는 Open Images의 `Tablet computer`와 Objects365의 `Tablet`이다 ([Open Images 상자 클래스 목록](https://storage.googleapis.com/openimages/v7/oidv7-class-descriptions-boxable.csv), [Objects365 클래스 목록](https://raw.githubusercontent.com/ultralytics/ultralytics/main/ultralytics/cfg/datasets/Objects365.yaml)).

조사자가 Open Images의 학습용 상자 파일 1,461만 행을 전부 읽어 세어 보니 **`Mobile phone` 상자는 6,365개, `Tablet computer`는 975개**였다 ([Open Images 학습 상자 CSV](https://storage.googleapis.com/openimages/v6/oidv6-train-annotations-bbox.csv)). COCO의 휴대폰 상자는 약 6,400개로 기억한다(기억). 그렇다면 Open Images로 학습한 모델이 COCO 모델보다 휴대폰을 더 많이 본 것은 아니다. 얻는 것은 태블릿과, 리모컨·계산기처럼 휴대폰과 헷갈리는 물건을 따로 떼어 낸 클래스다. 태블릿 975개는 한 종류를 배우기에 적으므로 기대를 낮게 잡아야 한다(추정). 휴대폰 상자의 47%에 "가려짐" 표시가 있지만 상자 넓이의 중앙값이 이미지의 14.7%로 크고, 이미지의 1% 미만인 작은 상자는 607개뿐이다. 웹캠에서 낮게 든 작은 휴대폰과는 거리가 있다. Objects365는 약 200만 장·3,000만 상자 규모지만 휴대폰·태블릿 상자 수는 확인하지 못했고, 공식 페이지에 라이선스 문구가 없어 2차 출처가 "CC BY 4.0"과 "상업 사용 불확실"로 갈린다 ([Objects365 개요](https://www.objects365.org/overview.html), [Ultralytics Objects365 문서](https://docs.ultralytics.com/datasets/detect/objects365/)).

**오픈 보캐뷸러리 모델**은 학습 때 정해진 종류 대신 글자로 준 단어("phone", "tablet")를 찾는 모델이다. YOLOE와 YOLO-World는 단어를 미리 정해 모델 안에 굳힌 뒤 보통 YOLO처럼 내보내는 것을 공식 지원하고, 굳힌 뒤에는 새 단어를 받지 못한다. 두 모델 모두 Objects365로 학습했으므로 휴대폰과 태블릿을 상자로 본 적이 있다. 같은 계열이라도 OWLv2와 Grounding DINO는 가장 작게 줄인 파일도 각각 128MB, 151MB라 브라우저에서 계속 돌리기에는 맞지 않고, 학습 데이터에 자동으로 상자를 달아 주는 오프라인 도구로 쓰는 편이 맞다 ([OWLv2 ONNX 변환본](https://huggingface.co/Xenova/owlv2-base-patch16-ensemble), [Grounding DINO tiny ONNX](https://huggingface.co/onnx-community/grounding-dino-tiny-ONNX)).

질문 (2)의 답은 "있다, 그러나 조건이 붙는다"이다. 작고 문서가 살아 있는 것은 전부 AGPL-3.0 또는 GPL-3.0이다. Apache-2.0 쪽은 오래됐거나(2018년 SSD), 더 무겁거나(D-FINE-S 10M), 가중치의 데이터 조건이 불분명하다. 그리고 600종·365종을 작은 모델에 담아 전체 mAP가 16~18로 낮고, 휴대폰·태블릿 한 종류의 점수는 공개돼 있지 않다. 리모컨·계산기·지갑을 따로 배웠으니 검은 직사각형을 전부 휴대폰으로 모는 오판은 줄 가능성이 있지만(추정), 팀이 알고 있는 "자연스럽게 쥔 휴대폰은 약 11%만 잡힌다"는 문제(팀 자체 측정으로 노트에 적힌 값. 이번에 다시 재지 않았다)가 나아질지는 같은 시험 영상으로 재야 한다.

### 손에 든 휴대폰 데이터는 FPI-Det이 가장 쓸 만하고, 웹캠 정면 데이터는 사실상 없다

직접 학습할 때 쓸 공개 데이터도 살폈다. **FPI-Det**은 22,879장에 휴대폰 상자 10,255개, 통화·사용 자세가 들어 있고 저장소 라이선스가 MIT다. 다만 감시 카메라처럼 멀리서 내려다본 시점이 많고 휴대폰이 20×20픽셀까지 작다 ([FPI-Det 논문](https://arxiv.org/html/2509.09111v1), [FPI-Det README](https://raw.githubusercontent.com/KvCgRv/FPI-Det/main/README.md)). 원본 이미지가 대회 자료에서 왔는데 그쪽 재배포 조건은 확인하지 못했다. HICO-DET은 휴대폰에 대해 `hold`, `talk_on`, `text_on`을 따로 표시해 "들고만 있음·통화·문자" 장면을 골라낼 수 있다 ([HICO-DET 상호작용 목록](https://raw.githubusercontent.com/zhihou7/HOI-CL/master/misc/hico_list_hoi.txt)). "휴대폰 없이 귀 옆에 댄 손"은 손동작 데이터인 HaGRID의 `call` 클래스가 가장 가깝다. 엄지와 새끼손가락을 편 전화 손 모양이라 맨손을 귀에 댄 모습과 손 모양은 다르지만 위치는 같다. 라이선스는 "CC BY-SA 4.0의 변형"이라고만 적혀 있고 변형 조항은 읽지 못했다 ([HaGRID README](https://raw.githubusercontent.com/hukenovs/hagrid/master/README.md)). 노트북 웹캠 정면에서 손에 든 휴대폰에 상자까지 달린 공개 데이터는 Roboflow Universe의 개인 프로젝트 몇 개와 온라인 시험 감독용 소규모 자료뿐이고, 전부 검색 요약으로만 봐서 장수·품질·라이선스를 하나씩 열어 확인해야 한다(스니펫) ([Roboflow 'Phone' or 'tab'](https://universe.roboflow.com/alamin/phone-or-tab)). 운전자 데이터는 대부분 사진 단위 라벨이라 상자가 없고 연구 전용 조건이 많다.

**미세 조정**은 이미 학습된 모델을 우리 사진으로 조금 더 학습시키는 일이다. 방법은 크게 여덟 가지이고, 추정 노력은 출처가 있는 수치가 아니라 조사자의 추정이다.

### "새 라이브러리 없이"를 지키는 길은 A와 B이고, 둘 다 같은 낡은 도구에 기댄다

MediaPipe Model Maker는 메타데이터가 든 `.tflite`를 내보내 지금 코드에 그대로 들어간다는 점에서 조건에 가장 잘 맞는다. 고를 수 있는 구조는 MobileNetV2 256·320과 MobileNet-MultiHW-AVG 256·384 네 가지이고 EfficientDet은 지원하지 않는다 ([Model Maker 모델 목록 소스](https://github.com/google-ai-edge/mediapipe/blob/master/mediapipe/model_maker/python/vision/object_detector/model_spec.py)). 휴대폰과 태블릿 두 종류로 학습하면 질문 (2)도 함께 풀린다.

문제는 이 도구가 **사실상 지원이 끝났다**는 점이다. 패키지 최신판은 2024-04-22 이후 갱신이 없다 ([PyPI](https://pypi.org/pypi/mediapipe-model-maker/json)). 2026-11-15에 MediaPipe 이슈 담당 계정이 더는 적극 지원하지 않는다고 답했고 ([mediapipe#4779](https://github.com/google-ai-edge/mediapipe/issues/4779)), 공식 학습 노트북은 2026-11-10에 샘플 저장소에서 삭제됐으며 ([삭제 커밋](https://github.com/google-ai-edge/mediapipe-samples/commit/bb7f0b2aee6de46d1e32dba3ced12c8152211680)), 공식 가이드 주소는 이제 다른 페이지로 넘어간다. 설치도 걸린다. 지원 파이썬은 3.8~3.10인데 ([mediapipe#6013](https://github.com/google-ai-edge/mediapipe/issues/6013)) 지금 Colab에서 고를 수 있는 런타임은 3.12와 3.13뿐이다 ([Colab 런타임 안내](https://research.google.com/colaboratory/runtime-version-faq.html)). 의존 패키지 하나가 Apple Silicon과 Windows용 파일을 내지 않아, 협력자는 이 두 환경에는 최신판을 설치할 수 없다고 답했다 ([mediapipe#5545](https://github.com/google-ai-edge/mediapipe/issues/5545)). 그 패키지를 빼고 설치하는 우회법과 Colab에 파이썬 3.11을 따로 까는 방법이 이슈에 안내돼 있지만 ([mediapipe#5080](https://github.com/google-ai-edge/mediapipe/issues/5080), [mediapipe#6070](https://github.com/google-ai-edge/mediapipe/issues/6070)), 2026-11 현재 실제로 되는지는 돌려 보지 않았다. 2026년 2~3월에는 학습에 필요한 사전학습 파일이 한 달 동안 내려받아지지 않은 적도 있다 ([mediapipe#6235](https://github.com/google-ai-edge/mediapipe/issues/6235)). 삭제 직전 노트북은 옛 커밋에 남아 있고 아래 사양은 거기서 읽었다 ([삭제 전 감지기 노트북](https://github.com/google-ai-edge/mediapipe-samples/blob/65a0057ca4a8f11a993767bde7e2cde602b05707/examples/customization/object_detector.ipynb)). 이 길을 택한다면 설치에 성공한 환경과 사전학습 파일을 팀 드라이브에 따로 보관해 두는 편이 안전하다(추정).

정확도 면에서도 조심할 것이 있다. 공식 예제(62장)에서 int8로 만드는 과정(QAT)은 점수를 13~19%p 떨어뜨렸으므로, 오판이 문제인 우리 용도에서는 float16을 먼저 쓰는 편이 낫다(추정). 입력이 256·320이라 멀리 든 휴대폰은 수십 픽셀로 줄고, 한 사용자는 MobileNetV2가 작은 물체에서 EfficientDet보다 훨씬 나빴다고 적었다(일화) ([mediapipe#4420](https://github.com/google-ai-edge/mediapipe/issues/4420)). 그리고 Model Maker로 만든 모델이 **웹** ObjectDetector에서 돈다는 공식 문장이나 재현 사례는 확인하지 못했다. 다른 도구로 만든 EfficientDet 모델에 MediaPipe용 메타데이터를 써넣어 돌렸다는 사용자가 있는데, 자바스크립트에서는 CPU 위임에서만 됐다고 한다(일화) ([mediapipe#6235](https://github.com/google-ai-edge/mediapipe/issues/6235)).

### 가장 싼 학습은 상자가 필요 없는 "잘라 낸 사진 분류기"다

경로 B는 감지기를 새로 만드는 대신, 이미 가진 얼굴·자세 랜드마크로 귀 옆이나 손목 주변을 잘라 낸 작은 사진이 "휴대폰 있음"인지 "없음"인지만 가리는 분류 모델을 만드는 것이다. 사진을 종류별 폴더에 넣기만 하면 되어 상자를 그릴 필요가 없고, 같은 `@mediapipe/tasks-vision` 안의 ImageClassifier로 불러올 수 있어 새 라이브러리가 필요 없다 ([삭제 전 분류기 노트북](https://github.com/google-ai-edge/mediapipe-samples/blob/65a0057ca4a8f11a993767bde7e2cde602b05707/examples/customization/image_classifier.ipynb), [Image Classifier 웹 가이드](https://developers.google.com/edge/mediapipe/solutions/vision/image_classifier/web_js)). 데이터 양의 감은 이렇다. TensorFlow 공식 튜토리얼은 종류당 1,000장으로 고양이·개를 96~98% 맞혔고, Model Maker 예제는 종류당 600~800장으로 꽃 5종을 85~91% 맞혔다 ([TensorFlow 전이학습 튜토리얼](https://www.tensorflow.org/tutorials/images/transfer_learning)). 다만 귀 옆 맨손과 귀 옆 휴대폰은 고양이와 개보다 훨씬 비슷하게 생겼고, **이 구분을 작은 분류기로 해낸 공개 수치는 찾지 못했다.** 종류당 1,000장 안팎을 1차 목표로 잡되(추정), 장수보다 사람·장소·촬영 회차의 다양성이 더 중요하다. 분류기 한 번은 Pixel 6 CPU에서 15~24ms 수준이다(EfficientNet-Lite0 기준) ([Image Classifier 안내](https://developers.google.com/edge/mediapipe/solutions/vision/image_classifier)). Model Maker 설치를 피하려면 지금 Colab의 Keras로 학습하고 TFLite로 바꾼 뒤 MediaPipe의 메타데이터 작성기로 설명서를 넣는 길이 있으나, 끝까지 이어 돌린 사례는 확인하지 못했다 ([MediaPipe 메타데이터 작성기](https://github.com/google-ai-edge/mediapipe/tree/master/mediapipe/tasks/python/metadata/metadata_writers)).

### 데이터와 평가: 실제 웹캠으로 찍은 "헷갈리는 음성 사진"이 장수보다 중요하다

감지기를 미세 조정할 때 권장 상자 수는 출처마다 다르다. Vertex AI는 종류당 약 1,000개를 권하고 학습 데이터가 실제 쓰일 장면과 최대한 같아야 한다고 적는다 ([Vertex AI 데이터 준비](https://docs.cloud.google.com/vertex-ai/docs/image-data/object-detection/prepare-data)). Ultralytics는 종류당 1,500장·상자 1만 개 이상을 권하고, 오판을 줄이려면 아무 상자도 없는 배경 사진을 0~10% 섞으라고 한다 ([Ultralytics 학습 요령](https://docs.ultralytics.com/yolov5/tutorials/tips_for_best_training_results/)). 3명이 몇 주 안에 채울 수 있는 현실적인 목표는 종류당 500~1,000개다(추정). 우리 실패 유형에서는 **하드 네거티브**(모델이 헷갈려 하는 음성 사진: 귀 옆 맨손, 턱 괸 손, 필통·계산기·리모컨·지갑)를 넣는 것이 양보다 중요하다. 차량용 휴대폰 감지 업체 LightMetrics도 빈손에 경보가 나는 문제를 겪었고, 외부 데이터보다 자사 카메라로 찍은 데이터로만 학습한 것이 가장 크게 도움이 됐다고 적었다. 전후 수치는 없는 업체 홍보 글이다 ([LightMetrics 블로그](https://www.lightmetrics.ai/resources/blogs/the-road-to-99-precision-overcoming-challenges-in-cell-phone-detection-accuracy)). Model Maker 감지기가 상자 없는 음성 사진을 받아 주는지는 확인하지 못했다.

상자를 그리는 도구는 Label Studio(Apache-2.0)와 CVAT(MIT)를 내 컴퓨터에 설치하면 사진이 밖으로 나가지 않는다 ([Label Studio](https://github.com/HumanSignal/label-studio), [CVAT](https://github.com/cvat-ai/cvat)). Roboflow나 CVAT Online 무료판은 사진이 그쪽 서버로 간다. 큰 모델로 상자를 자동으로 달고 작은 모델을 학습시키는 Autodistill도 내 장비에서 돌릴 수 있지만 자동 상자는 완벽하지 않다고 문서가 적는다 ([Autodistill 문서](https://docs.autodistill.com/)).

여기에 **팀이 정해야 할 개인정보 문제**가 있다. 서비스 사용자의 웹캠 영상은 어떤 경로로도 학습에 쓰지 않는다. 이것은 결정이 아니라 전제다. 반면 팀원이 일부러 찍은 학습용 사진을 Colab·Roboflow·Teachable Machine 같은 외부 서비스에 올릴지는 팀이 정해야 한다. Colab에서 학습하면 사진은 어차피 Google 서버에 올라간다. 저장소가 공개이므로 이 사진들은 git에도 올리지 않는다.

평가는 두 가지를 지킨다. 첫째, 시험용 사진은 사진 단위가 아니라 **사람·촬영 회차 단위**로 떼어 둔다. 같은 사람의 연속 프레임이 학습과 시험 양쪽에 들어가면 점수가 실제보다 높게 나온다 ([scikit-learn 교차 검증 문서](https://scikit-learn.org/stable/modules/cross_validation.html)). 팀원이 3명뿐이므로 최종 시험에는 학습에 나오지 않은 사람과 장소를 넣는 것이 좋다(추정). 둘째, 오판이 놓침보다 비쌀 때는 정확도나 mAP가 아니라 **오탐률을 먼저 고정하고 그때의 재현율**을 본다. **오탐**은 없는데 있다고 한 것, **재현율**은 실제로 있는 것 중 잡아낸 비율이다 ([Google ML 단기 과정](https://developers.google.com/machine-learning/crash-course/classification/accuracy-precision-recall)). 우리 서비스에 맞춘 보고 방식으로는 "휴대폰 없는 공부 1시간당 오판 횟수(연속 3초 규칙까지 적용한 뒤)"와 그 조건에서의 재현율을 유형별로 따로 세는 것을 권한다(추정).

질문 (3)의 답을 한 줄로 줄이면 이렇다. 학습 자체는 수 분에서 수 시간이면 끝나고 학부생 3명이 할 수 있다. 어려운 부분은 설치 환경을 맞추는 일(며칠, 실패 가능성 있음)과 실제 웹캠 조건의 데이터를 1~2주 모으는 일이며, 위 표의 항목을 더하면 분류기(B)는 1~2주, 감지기 재학습(A)은 2~3주쯤이고, 설치가 막히면 더 늘어난다(추정).

## 귀 옆 맨손과 귀 옆 휴대폰을 가른 공개 사례는 없다: 그래서 구분보다 억제가 먼저다

### "통화 감지"라고 불리는 시스템 대부분은 휴대폰이 아니라 손의 위치를 본다

운전자 통화 감지 연구를 읽어 보면 높은 정확도는 "손이 얼굴 옆에 있으면 통화"라는 가정에서 나온다. Le 외(2016)는 얼굴과 손을 찾아 손이 얼굴 옆에 붙어 있으면 통화로 판정해 정확도 0.942를 보고했는데, 휴대폰은 아예 찾지 않는다. 이유는 사용 중인 휴대폰이 대부분 가려져 사람 눈으로도 안 보이기 때문이라고 적었다 ([Le 외 2016](https://www.cv-foundation.org/openaccess/content_cvpr_2016_workshops/w3/papers/Le_Multiple_Scale_Faster-RCNN_CVPR_2016_paper.pdf)). Li 외(2020)는 오른손과 오른쪽 귀의 상자 위치만으로 통화를 판정해 정밀도 0.79, 재현율 0.86을 냈다. 이 방식은 맨손을 귀에 대도 통화가 된다 ([Li 외 2020](https://par.nsf.gov/servlets/purl/10184753)). Artan 외(2014)는 얼굴 주변을 잘라 분류해 정확도 86%를 냈지만 오경보가 "얼굴 일부를 무언가가 가릴 때" 난다고 적었고 맨손 음성 사진을 따로 두지 않았다 ([Artan 외 2014](https://www.cv-foundation.org/openaccess/content_cvpr_workshops_2014/W04/papers/Artan_Driver_Cell_Phone_2014_CVPR_paper.pdf)). **읽은 문헌 가운데 귀 옆 맨손을 음성 예시로 두고 귀 옆 휴대폰과 갈라 낸 결과를 보고한 것은 없다.** 운전 중에는 "손이 얼굴 옆 = 통화"가 거의 맞지만, 공부 중에는 턱을 괴거나 머리를 만지는 일이 흔하므로 같은 방식은 지금의 오판을 그대로 되풀이한다(추정).

귀·볼 옆 맨손이 휴대폰으로 잡히는 이유는 모델이 "손에 쥔 채 얼굴 옆에 있는 것"이라는 주변 모습에 반응하기 때문이라는 설명이 가장 그럴듯하다. 다만 이것을 "cell phone"에 대해 수치로 잰 논문은 찾지 못했다. 간접 근거로, 사람과 함께 나오는 손에 드는 물건은 주변 모습에 크게 기대어 인식된다는 연구가 있고(가장 심한 20쌍에 "리모컨–사람"이 있고 휴대폰은 없다) ([Singh 외 2020](https://arxiv.org/pdf/2001.03152)), LightMetrics가 자사 모델이 손·손가락 위치를 주된 단서로 삼아 빈손에 경보를 냈다고 적은 것이 있다 ([LightMetrics 블로그](https://www.lightmetrics.ai/resources/blogs/the-road-to-99-precision-overcoming-challenges-in-cell-phone-detection-accuracy)). 이 문제가 Lite0만의 것인지 COCO로 학습한 감지기 공통인지는 확인하지 못했다. 그러니 모델을 바꾸면 이 오판이 사라진다고 볼 근거가 없고, 팀이 직접 본 현상이 사실상 유일한 근거다.

손 모양으로 가르는 길도 근거가 약하다. "이 손이 무언가를 쥐고 있는가"를 내는 감지기(100DOH)가 있지만 브라우저에 올릴 수 없는 큰 모델이고, 손이 물체 가까이 있을 때 접촉 여부를 맞히는 것이 흔한 실패라고 저자가 적었다 ([Shan 외 2020](https://arxiv.org/pdf/2006.06669)). 운전자의 손 모양으로 "휴대폰 쥠"을 가린 연구는 그 클래스 정확도가 0.04~0.53에 그쳤다 ([운전자 손 쥠 분석](https://arxiv.org/pdf/1802.07854)). MediaPipe Hand Landmarker(손가락 21점)를 더하면 모델이 네 개가 되어 발열 문제와 정면으로 부딪히고, 귀에 댄 손은 손가락이 머리에 가려 점 자체가 불안정할 가능성이 높다(추정).

### 지금 방어할 수 있는 규칙: 귀·볼 영역의 검출은 휴대폰으로 올리지 않는다

구분이 검증되지 않았으니, 오판을 없애는 가장 확실한 방법은 구분을 포기하고 그 영역을 판정에서 빼는 것이다. 얼굴 랜드마크로 귀·볼 옆 영역을 만들고, 감지 상자의 중심이 그 안이면 `phone`으로 올리지 않는다. 새 라이브러리도 학습도 필요 없다. 대가는 분명하다. **귀에 대고 실제로 통화하는 경우를 놓친다.**

이 대가를 받아들일 근거가 있다. 유럽 자동차 안전 평가(Euro NCAP)의 운전자 감시 기준은 휴대폰 사용을 "시선이 반복해서 휴대폰으로 가는 것"으로 정의하고, 시험 위치(무릎 위, 거치대, 운전대 주변 등)에 귀에 댄 통화 자세를 넣지 않았다. 손이 얼굴에 가는 행동(눈 비비기)에서 시스템이 정상 동작할 것도 요구하지 않는다 ([Euro NCAP 운전자 관여 프로토콜 v1.2](https://cdn.euroncap.com/cars/assets/Euro_NCAP_Protocol_Safe_Driving_Driver_Engagement_v1_2_ebce03a443.pdf)). 사람 목숨이 걸린 분야의 기준도 귀 옆 통화를 필수로 잡으라고 하지 않는다는 뜻이다. 이 기준이 허용하는 오경보 횟수의 숫자는 확인하지 못했다. 공부 인증에서는 "공부했는데 휴대폰 사용으로 기록되는" 오판이 놓침보다 신뢰를 더 해친다는 팀의 우선순위와도 맞는다.

함께 쓸 수 있는 보조 규칙과 그 한계는 다음과 같다. 얼굴 폭에 비해 상자가 휴대폰이라기엔 지나치게 크면 버리는 **크기 조건**은 근거가 있다. 손목 주변 영역과 겹치는 검출만 인정하는 **손목 조건**은 한 연구에서 오검출을 70% 줄이면서 정검출을 17% 잃었지만 ([SHOP](https://ar5iv.labs.arxiv.org/html/2203.15228)), 귀 옆 맨손은 손목 조건을 통과하므로 이 문제에는 도움이 안 되고 책상 위 물건 오판에 쓸모가 있다. 연속해서 여러 번 잡혀야 인정하는 **지속 조건**은 귀 옆 맨손이 거의 매번 잡히기 때문에 이것만으로는 걸러지지 않는다. 입 움직임을 함께 보는 방법은 근거가 거의 없고, 듣기만 하는 통화를 놓치며 소리 내어 읽는 공부를 오판할 수 있다(추정).

귀 옆 실제 통화까지 잡고 싶다면 문헌상 가장 가까운 길은 앞 절의 경로 B, 곧 귀 옆 영역을 잘라 맨손 음성 사진을 많이 넣어 학습한 이진 분류기다. 그러나 성공을 뒷받침하는 공개 수치가 없다. 질문 (4)의 정확한 답은 "구분할 수 있다"도 "없다"도 아니고 **"공개된 성공 사례가 없으므로 직접 실험해 봐야 안다, 그 전까지는 억제 규칙으로 오판부터 없앤다"** 이다.

완전히 가려진 휴대폰은 화소 정보가 없으니 어떤 감지기로도 잡을 수 없다는 점도 적어 둔다(추정). 손 주변을 잘라 크게 넣는 방법은 다음 절에서 다룬다.

## 발열을 정하는 것은 1초에 한 번 도는 감지기가 아니라 매 프레임 도는 것들과 GPU 다툼이다

### 감지기의 계산 몫은 작다고 추정된다

브라우저 안 추론의 전력이나 온도를 직접 잰 출판물은 찾지 못했다. 그래서 아래는 지연 시간으로 어림한 것이고 방향만 믿을 수 있다. 감지기 한 번이 30~60ms라면 1초에 한 번 돌 때 일하는 시간은 전체의 3~6%다. 얼굴 모델은 매 프레임(초당 약 30번), 자세 모델은 초당 15번 돈다. 호출 횟수만 30배·15배다. 한 번의 비용이 비슷한 자릿수라면 **감지기의 계산 몫은 전체의 몇 퍼센트 수준**이다(추정). 발열을 크게 줄이려면 감지기 교체보다 얼굴 모델의 호출 빈도, 3D 화면의 프레임 수와 해상도, 그리고 아래의 GPU 다툼을 먼저 봐야 한다.

### 호출 횟수와 무관하게 드는 비용: GPU를 나눠 쓰는 다툼

MediaPipe의 웹 비전 작업은 WebGPU가 아니라 WebGL로 GPU를 쓴다고 관리자가 답했다 ([mediapipe#5826](https://github.com/google-ai-edge/mediapipe/issues/5826)). **WebGL 컨텍스트**는 웹 페이지가 GPU를 쓰기 위해 여는 작업 공간이다. 설치된 `@mediapipe/tasks-vision` 1.0.1의 배포 파일을 열어 보면, 캔버스를 따로 넘기지 않을 때 GPU 작업마다 새 캔버스를 만들어 컨텍스트를 얻는다(로컬 파일 확인). 우리 코드는 얼굴·자세·휴대폰 세 작업 모두 GPU 위임이므로, Three.js까지 한 탭에 컨텍스트가 넷일 가능성이 높고 같은 웹캠 프레임이 작업마다 따로 GPU로 올라간다(추정).

PC 50대와 모바일 20대에서 브라우저 추론을 잰 연구가 이 구성이 왜 문제인지 보여 준다. 추론을 돌리는 동안 화면 프레임은 평균적으로 CPU 추론일 때 36.2%, **내장 GPU 추론일 때 44.3%**, 외장 GPU일 때 8.1% 떨어졌다. 저자들은 GPU 추론이 더 빠르긴 해도 내장 GPU에서는 화면 그리기와 자원을 다투므로 CPU(WASM) 실행이 화면을 더 부드럽게 한다고 정리했고, 추론이 오래 걸리는 것과 화면이 버벅이는 것 사이에는 상관이 없었다고 적었다 ([브라우저 추론 측정 연구](https://arxiv.org/pdf/2402.05981)). 이 연구는 MediaPipe가 아니고 추론을 계속 돌린 조건이라 우리 앱에 그대로 옮길 수는 없다. 그래도 "노트북 내장 GPU에서 3D 화면과 모델 세 개가 GPU를 다툰다"가 끊김의 유력한 원인이라는 방향은 맞는다(추정).

### 감지기 쪽에서 줄일 수 있는 것 네 가지

첫째, **int8 모델을 CPU 위임으로 돌린다.** Pixel 6에서 Lite0 int8의 CPU 지연(29.31ms)은 지금 쓰는 float16의 GPU 지연(27.97ms)과 거의 같다. 1초에 한 번이라면 걸리는 시간은 비슷하게 두면서 GPU를 3D 화면과 얼굴 모델에 넘기고 컨텍스트 하나를 없앨 수 있다. 바꿀 것은 모델 주소와 위임 옵션뿐이고 새 라이브러리가 필요 없다. 노트북 브라우저에서도 같은 관계가 성립하는지는 재 봐야 한다. int8 모델을 GPU 위임으로 돌리는 조합은 권하지 않는다. 공식 표가 그 칸을 비워 두었고, 웹에서 이 조합이 조용히 CPU로 넘어가는지 오류를 내는지 확인하지 못했다 ([MediaPipe Object Detector 가이드](https://developers.google.com/edge/mediapipe/solutions/vision/object_detector), [LiteRT GPU 위임 문서](https://developers.google.com/edge/litert/performance/gpu)).

둘째, **손 주변을 잘라서 넣는다.** MediaPipe 웹 ObjectDetector는 "이 부분만 봐라"는 관심 영역 옵션을 받지 않으므로 캔버스에 직접 잘라 그려서 넘겨야 한다 ([mediapipe#6148](https://github.com/google-ai-edge/mediapipe/issues/6148)). 모델 입력은 320×320으로 고정이라 잘라 넣어도 추론 비용은 같다. 640×480 전체를 넣으면 가로가 절반으로 줄지만, 손 주변 240×240을 잘라 넣으면 1.33배로 커져 같은 휴대폰이 가로 기준 약 2.7배 많은 화소로 들어간다(조사자 계산). 물체가 화면에서 차지하는 비율이 커지면 검출이 좋아진다는 것은 다른 물체에서 확인된 경향이다(손 크기 10%→20%에서 검출 점수 78.2→90.3) ([Shan 외 2020](https://arxiv.org/pdf/2006.06669)). 이것은 발열을 줄이는 방법이 아니라 **비용을 늘리지 않고 자연스럽게 쥔 휴대폰의 검출률을 올릴 가능성이 있는 가장 싼 변경**이다. 휴대폰에 대해 전후를 잰 공개 수치는 없고, 귀 옆 맨손 오판에는 오히려 불리할 수 있다(손이 더 크게 보이므로. 추정). 그래서 귀·볼 억제 규칙이 먼저 있어야 한다.

셋째, **필요할 때만 돌린다(듀티 사이클링).** MediaPipe 자신도 손 추적에서 비싼 검출 단계는 손을 놓쳤을 때만 다시 돌린다 ([Hand Landmarker 문서](https://developers.google.com/edge/mediapipe/solutions/vision/hand_landmarker)). 같은 원리로, 이미 나오는 자세 결과에서 손목이 화면에 보일 때만 감지기를 돌리고 아니면 건너뛰거나 주기를 늘릴 수 있다. 다만 앞의 어림대로 감지기 몫이 작으므로 발열 절감 폭도 작을 것이고, 조건부 실행이 놓침을 얼마나 늘리는지 잰 공개 자료는 없다. 같은 방법을 매 프레임 도는 얼굴 모델에 적용하는 쪽이 절감 폭이 클 것이다(추정). 또 우리 앱처럼 실시간 연결(WebSocket)을 쓰는 탭은 숨겨져도 브라우저가 타이머를 늦추지 않으므로, 탭이 숨겨졌을 때 무엇을 끌지는 코드에서 직접 정해야 한다 ([MDN Page Visibility API](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API)).

넷째, **Worker로 옮긴다.** **Worker**는 화면을 그리는 주 흐름과 따로 도는 백그라운드 흐름이다. 감지기 호출이 1초마다 주 흐름을 수십 ms 막으면 발열과 별개로 "주기적으로 툭 끊기는" 느낌이 날 수 있다. MediaPipe 작업을 Worker에서 돌리는 것은 2026-06부터 된다고 관리자가 공식 예제와 함께 안내했다 ([mediapipe#5169](https://github.com/google-ai-edge/mediapipe/issues/5169), [공식 Worker 예제](https://github.com/google-ai-edge/mediapipe-samples-web/blob/main/src/workers/face-landmarker.worker.ts)). 이것은 끊김 대책이지 발열 대책이 아니다. GPU 사용 총량은 줄지 않는다.

### 실행 라이브러리를 바꾸는 것은 발열 대책으로 근거가 약하다

WebGPU는 2025-11 기준 주요 브라우저에 기본으로 들어왔지만 Linux와 구형 macOS 등에 빈 곳이 있어 CPU 대체 경로가 꼭 필요하다 ([web.dev WebGPU 지원 현황](https://web.dev/blog/webgpu-supported-major-browsers)). 1초에 한 번 도는 작은 감지기를 WebGPU로 옮겨 얻는 속도 이득은 체감되지 않을 것이고, 라이브러리를 하나 더 넣으면 묶음·메모리·GPU 작업 공간이 늘어난다(추정). 작은 감지기에서 WebGPU·WebGL·WASM의 속도와 전력을 비교한 수치는 찾지 못했다. 다른 라이브러리에서 CPU 여러 코어를 쓰려면 사이트에 교차 출처 격리 헤더(COOP·COEP)를 켜야 하는데, 이 헤더는 다른 주소에서 받아 오는 자원(모델 파일, 외부 API)에 추가 대응을 요구해 배포 설정까지 건드리게 된다 ([ONNX Runtime Web 환경 설정 문서](https://onnxruntime.ai/docs/tutorials/web/env-flags-and-session-options.html)). 설치된 MediaPipe 1.0.1에는 여러 코어용 파일이 없어 이 헤더를 켜도 MediaPipe에는 이득이 없을 가능성이 높다(로컬 파일 확인, 해석은 추정).

질문 (5)의 답은 이렇다. 비용을 정하는 것은 매 프레임 도는 얼굴 모델과 3D 화면, 그리고 그것들이 감지기·자세 모델과 내장 GPU를 다투는 구조다. 감지기 쪽에서 줄일 수 있는 것은 "GPU에서 내리기(int8+CPU)", "필요할 때만 돌리기", "주 흐름 밖으로 빼기"이고, 모델을 더 작은 것으로 바꿔서 얻는 발열 절감은 작을 것이다. 전부 추정이므로 모델을 하나씩 끄고 켜며 직접 재야 확정된다.

| 5 | **감지기 교체.** `onnxruntime-web` + PP-PicoDet(Apache-2.0)을 0번 시험 영상으로 Lite0과 비교한다. YOLO26n은 상한 참고용으로만 재고, 채택은 AGPL-3.0을 팀이 받아들일 때만 | **있음 (팀 확인)** | 선택 | 같은 시험 영상에서의 검출률·오판·ms·FPS | 수치로 이길 때만 교체 |

태블릿은 따로 판단해야 한다. 태블릿을 아는 가볍고 문서가 살아 있는 기성 모델은 전부 AGPL·GPL이므로, 태블릿 감지가 꼭 필요하다면 "AGPL-3.0을 받아들이고 5번에서 YOLOv8n-OIV7이나 YOLO26n-Objects365를 잰다"와 "Model Maker로 휴대폰·태블릿 두 종류 감지기를 직접 학습한다(지원이 끝난 도구)" 중에서 골라야 한다. 어느 쪽이든 5번까지 간 뒤의 일이고, 그 전에 팀이 태블릿 감지가 정말 필요한지부터 정하는 것이 순서다.

0번을 건너뛰면 안 되는 이유가 이 조사의 요지다. 공개된 수치는 전부 COCO 평균과 휴대폰 CPU 속도이고, 우리 문제인 "웹캠 앞 책상 장면의 휴대폰"과 "노트북 브라우저의 발열"에 대한 수치는 하나도 없다. 팀의 시험 영상만이 1~5번을 채택할지 버릴지 정해 준다. 시험 영상은 사용자 영상이 아니라 팀원이 동의하고 찍은 것이어야 하며, 저장소에 올리지 않는다.

## 결론

이 조사로 질문 자체가 바뀌었다. "더 나은 모델이 있는가"로 시작했지만, 두 실패는 원인이 달라 모델 하나를 바꿔서 함께 풀리지 않는다. 귀 옆 맨손 오판은 모델이 주변 모습에 반응하는 문제라 규칙이나 우리 데이터로 풀어야 하고, 자연스럽게 쥔 휴대폰을 놓치는 것은 화면에서 휴대폰이 차지하는 화소가 적은 문제라 잘라 넣기로 먼저 풀어 볼 수 있다. 발열은 감지기가 아니라 구조(매 프레임 도는 모델과 GPU 다툼)의 문제다. 세 가지 모두 새 라이브러리 없이 손댈 수 있는 곳에서 시작된다.

남는 결정은 기술이 아니라 팀 합의 세 가지다. 저장소를 AGPL-3.0으로 묶어도 되는가, 팀원이 찍은 학습용 사진을 외부 서비스에 올려도 되는가, 태블릿 감지와 귀 옆 통화 감지가 정말 필요한가. 그리고 하나 더, 직접 학습을 택한다면 서둘러야 할 이유가 있다. 그 길의 공식 가이드와 노트북이 조사 며칠 전에 삭제됐고, 지금은 받을 수 있는 파일이 내일도 받아진다는 보장이 없다.
